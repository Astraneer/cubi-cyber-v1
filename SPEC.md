## 1. Продукт: что строим

### 1.1. Суть
Мультиплеерная воксельная игра в духе Minecraft Java 1.21.1 «но лучше»: те же ощущения движения и механик, но
красивее, ровнее и масштабнее. Мир полностью изменяемый и живой. Сервер авторитетный. Клиент — один код на Rust:
**нативно под Windows** и **в браузере через WebGPU** (WASM).

### 1.2. Главные ценности заказчика (жёсткие требования, порядок важности)
1. **Ровные 60 к/с без рывков и без задержки ввода.** Ровность важнее среднего FPS. Рывки и «качели» качества — дефект.
2. **Картинка чёткая, «без мыла».** Нет TAA по умолчанию, нет нецелочисленного апскейла по умолчанию, тексели резкие.
3. **MSAA и тени никогда не выключаются автоматически.** Автоподстройка трогает другие рычаги (§6.10).
4. **Красиво и «вкусно»**: атмосфера, дымка, вода, облака, свет блоков — но не ценой п.1–3.
5. **Ощущения Minecraft**: движение, прыжок, бег, присед, ломание, бой — числа как в Java 1.21.1.
6. **Дальность**: мир виден далеко (цель — 1024 чанка горизонта), постройки игроков видны издалека.

### 1.3. Что уже решено заказчиком и переносится как требования (из донора)
Источник — донор; это **поведение, которое нужно воспроизвести** (golden-тесты §8.3):
- **Движение игрока**: физика Java 1.21.1, 20 тиков/с, интерполяция на кадр; ходьба, бег (Ctrl), присед (Shift),
  прыжок, плавание, лестницы, ступеньки, урон от падения. Донор: `donor/crates/voxel-core/src/game/player.rs`,
  `physics.rs`, `hazards.rs`, `third.rs`, `view.rs`, тесты `flight_tests.rs`, `slice3_tests.rs`, `survival_tests.rs`.
- **Полёт**: F — полёт для всех в выживании по физике творческого полёта MC (10,9 б/с, с бегом 21,8, вверх/вниз 7,5);
  выключил в воздухе — падаешь с уроном от высоты выключения; «можно ли летать» — одна функция правил (`may_fly`).
  H — отладочный полёт сквозь стены (только с отладкой сервера).
- **Камера**: V — первое лицо ↔ третье лицо «из-за правого плеча», камера не заходит в блоки, своя модель видна.
- **Управление** — раскладка `donor/web/ui/keys.js` (переназначаемая): WASD, Пробел, Ctrl, Shift, E, Q, F, V, H,
  T (чат), «/» (команда), Tab (игроки), F1, F3, F8, R/U/A (рецепты в окне), O (настройки).
- **Выживание**: здоровье, урон, смерть с выпадением вещей, еда лечит, медленная регенерация, броня, вёдра, текучая
  вода, ферма, мобы (свинья, корова, овца, курица, зомби), PvP с защитой на спавне.
- **Перекрёсток** (спавн): защищённая площадь, витрина машин, доски-рецепты иконками, кнопки «день/ночь только для себя».
- **Mekanism** (срезы M1–M5 донора): энергия, сталь, обогащение, ветряк, куб, улучшения, удвоение (дробилка,
  очиститель, сепаратор, газы), логистика (транспортёры с видимыми предметами, трубы, трубки, насос). Числа и тесты
  «тик в тик» — в `donor/mekanism/aspects`, `donor/crates/voxel-core/src/world/mek/*`, `mek*_tests.rs`.
- **Роли и команды**: владелец/админы/игроки, команды с подсказками и Tab, творческий режим, наблюдатель, `/rollback`.
- **NEI**: панель всех предметов, R/U рецепты и применения (включая машины), «+» в верстак, закладки, выдача в творческом.
- **Звук**: набор CC0/CC-BY по умолчанию (`donor/web/sounds`, CREDITS обязательны) + импорт звуков из своего
  `.minecraft` **только в браузер/на диск игрока**, никогда на сервер.
- **Наборы ресурсов**: загрузка zip-пака MC (labPBR) локально; пак AVPBR не входит в репо (права), грузится как внешний.
- **Настройки**: единая схема по разделам, пресеты «По умолчанию / Тяжелее / Свои», сброс раздела, без молчаливых
  перезаписей.
- **Отладка**: F3 (график кадров по причинам), F8 (баг-репорт с последними 10 с самописца и записью ввода для повтора).

### 1.4. Не делать (вне объёма)
Транспорт, самолёты, оружие огнестрельное, дороги, города (это было в другом проекте — не переносить). Модовые
загрузчики. Одиночная игра без сервера (локальный сервер в том же процессе — можно, это и есть одиночка).

пересобирает 524 288 клеток; тени дрожали (привязка каскадов не работала); авто-качество «качалось» и выключало
MSAA/тени; загрузка 7,8 МБ за кадр давала рывок 192 мс; первые вызовы шейдеров — рывки 0,1–1,2 с; дальний LOD
стирал постройки. Новый движок спроектирован так, чтобы эти классы проблем **не могли возникнуть** (§3–§6).

## 3. Целевые платформы и бюджеты

### 3.1. Платформы
- **Нативный клиент Windows** (wgpu: D3D12 основной, Vulkan запасной). Позже — Linux/macOS тем же кодом.
- **Браузер**: Chrome/Edge с WebGPU (WASM). Без WebGPU — понятное сообщение (WebGL не поддерживаем).
- **Сервер**: нативный Rust (Linux/Windows), без GPU.
- Один репо, один код ядра и рендера; платформенные «оболочки» тонкие.

### 3.2. Уровни железа (для пресетов и проверки)
| Уровень | Пример | Профиль по умолчанию |
|---|---|---|
| A | встроенная графика / телефон (WebGPU) | 720p–1080p, 60 Гц, дальность 128–256 |
| B | RTX 3050 Laptop (ноутбук заказчика, экран 3440×1440 120 Гц) | 1080p–3440×1440, 60 Гц, дальность 256 |
| C | RTX 4070 | 1440p, 120 Гц, дальность 512 |
| D | RTX 4090 | 4K60 или 1440p 144, дальность 1024 |

### 3.3. Бюджеты (проектные, проверяются на железе заказчика позже)
- Кадр 60 Гц = 16,7 мс; **цель GPU p95 ≤ 12 мс**, CPU кадра p95 ≤ 4 мс на уровне B. Для 120 Гц — вдвое меньше.
- Рывков > 25 мс на эталонном маршруте — ≤ 2 за прогон, > 50 мс — 0.
- Правка блока → видимый результат: **≤ 2 кадра**; финальный меш ≤ 100 мс.
- Тик сервера 20 Гц (как MC; механики и физика игрока на 20 Гц): **p99 ≤ 25 мс** при 32 игроках / 5 тыс. сущностей /
  10 тыс. машин / 100 тыс. активных клеток жидкости.
- Память клиента уровня B ≤ 2 ГБ CPU, ≤ 3 ГБ VRAM; уровня A ≤ 512 МБ / 512 МБ.

## 4. Архитектура ядра: «стоимость пропорциональна изменениям, а не миру»

Это **главное** в ТЗ. Всё остальное опирается на этот договор.

### 4.1. Крейты (стартовая раскладка)
```
crates/
  core-types     — координаты, ID, версии, ошибки, детерминированный RNG
  world          — пространства, регионы, страницы, компоненты, транзакции, журнал
  gen            — генератор мира (перенос v4 донора), асинхронный
  sim            — тики: блоки, жидкости, машины, логистика, сущности, игроки
  rules          — механики MC/Mekanism, рецепты, реестр (номера ID из донора)
  net            — протокол, дельты, AOI, предсказание
  save           — снимки + журнал, миграции
  jobs           — пул задач (native threads / web workers), бюджеты, версии
  render         — wgpu-рендер: граф кадра, terrain, LOD, модели, свет, пост
  ui             — интерфейс (egui или свой immediate-mode поверх render), один код для обеих платформ
  audio          — позиционный звук (native: cpal/kira; web: WebAudio через web-sys)
  telemetry      — самописец кадров, счётчики работы, F8
  client-native  — оболочка Windows (winit)
  client-web     — оболочка браузера (wasm-bindgen, canvas, workers)
  server         — авторитетный сервер
tools/           — импорт донора, сборка атласа, импорт паков, bench, генерация эталонов
```

### 4.2. Модель мира
- **Пространства** (`SpaceId`): земля = пространство 0; переносимые постройки — свои пространства с transform.
- **Регион** — единица стриминга/сохранения (например 32×32 колонки). **Страница 16³** — единица изменения, мешинга,
  симуляции клеток и сети. Высоту мира не фиксировать в формате (страницы по Y).
- Режимы страницы: `Uniform` (одно значение) / `Paletted` (палитра + упакованные индексы) / `Dense` (массив) с
  гистерезисом переходов. Клетка — `u32` (ID блока 16 бит + состояние 16 бит, как донор) — совместимость ID.
- **Каналы-маски** на страницу (битовые): occupancy, opaque, collidable, blocks_projectile, fluid, emitter. Свойства
  блока — из реестра; маски считаются при изменении.
- **Компоненты** (инвентари, машины, таймеры) — отдельное хранилище по стабильному ID, ссылка из клетки.
- **Свет игровой** (уровни 0–15 MC + RGB для вида) — отдельные поля страницы, не внутри меша.
- **Неизвестное ≠ воздух**: незагруженная страница — `Unknown`; запросы к ней не генерируют её синхронно, а
  возвращают «нет данных» (игровая логика решает, что делать: ждать, отказать).

### 4.3. Транзакции и журнал (сердце движка)
```rust
struct WorldChange {
    tx: TxId, tick: Tick, space: SpaceId,
    pages: SmallVec<[(PageId, Version /*before*/, Version /*after*/); 4]>,
    cells: SmallVec<[(LocalIdx, Cell /*old*/, Cell /*new*/); 8]>,
    components: SmallVec<[ComponentChange; 2]>,
    channels: ChannelMask,   // shape | collision | opacity | emission | fluid | contents | connections …
}
```
- Любое изменение мира — только через транзакцию. Связанные изменения (блок + содержимое + соединения + дроп) —
  атомарно.
- **Журнал** общий; у потребителей свои курсоры: мешинг, свет, LOD, сеть, сохранение, физика.
- Каждый производный кэш (меш страницы, световая страница, LOD-узел, сетевой снимок) хранит **версии входов**.
  Результат публикуется, только если входы не устарели; иначе задача перезапускается.
- **Два договора** на каждую систему: «что истинно сразу после commit» и «что доезжает позже, с каким бюджетом и
  максимальной задержкой». Записать оба в `docs/CONTRACTS.md`.
- Повторные визуальные изменения одной страницы объединяются (coalescing); **игровые события не схлопываются**.

### 4.4. Задачи и бюджеты
- Все тяжёлые работы — задачи `jobs` с ценой в **логических единицах** (клетки, квады, байты, лучи), версиями входов,
  отменой устаревших.
- Очереди ограничены по количеству, байтам и возрасту. Резерв для ближних интерактивных правок.
- **Ноль выделений памяти в кадре** на горячих путях (проверяется тестом с считающим аллокатором, §8.2).
- Браузер: web workers; при наличии cross-origin isolation — SharedArrayBuffer, иначе передача буферов.

### 4.5. Генерация
- Перенос генератора v4 донора **бит-в-бит** (тест пробы `PROBE_REF`, WASM = натив).
- Только асинхронно (задачи), никогда в горячем чтении. Предзагрузка по траектории игрока и по «времени до
  последствия».
- **Руды скрыты от клиента**: клиентский генератор получает только «публичный» слой (рельеф, биомы, поверхность);
  руды и подземные секреты — только с сервера по мере видимости. Иначе X-ray чит из сида.

## 5. Симуляция, сервер, сеть

### 5.1. Тик
- 20 Гц, как MC (механики «тик в тик» с донором). Порядок фаз фиксирован и детерминирован.
- **Активные множества**: клетки с запланированными тиками, жидкости по фронту, машины по событиям. Неактивное не
  обходится. Цена тика ∝ событиям, не размеру мира (§8.2 тест масштаба).
- Запланированные тики — с бюджетом в логических операциях и стабильным переносом остатка; возраст очереди — метрика.
- Сущности: плотные массивы компонентов (ECS-lite), **пространственный хэш** для соседства (никаких попарных обходов),
  спящие/активные.
- Машины и логистика: граф соединений; предметы в трубах — маршруты со временем прибытия; энергия/жидкость/газ — по
  компонентам сети. Целевое расширение — «автомат цепочки» (свёртка стабильной цепочки машин в события) с проверкой
  против подробного интерпретатора (§9 гипотеза H2).
- Детерминизм там, где нужен: рецепты, инвентари, энергия, логистика — стабильный порядок, никаких `HashMap`-порядков
  в результатах, RNG по ключу `seed+subsystem+id+event`.

### 5.2. Параллельность сервера
Этап 1: один владелец мира + рабочие задачи на снимках (генерация, мешинг для сети, поиск пути, сжатие), применение
результатов в фиксированной фазе. Этап 2 (по замерам): владение регионами и независимыми компонентами сетей, общий
commit тика.

### 5.3. Сеть
- WebSocket сейчас (браузер), WebTransport — когда доступно; нативный клиент — QUIC/UDP. Каналы: ввод, позиции
  (последнее состояние), надёжные действия/транзакции, крупные снимки (свой бюджет отправки).
- Сервер авторитетный; клиент предсказывает движение и правки (оверлей поверх подтверждённого), откат по ответу.
- Дельты страниц — относительно **подтверждённой** клиентом версии; нет истории — полный снимок страницы с палитрой.
- Большие операции (взрыв) — одна транзакция; при одинаковой базе — компактная детерминированная команда + проверка.
- Интерес по зоне (AOI) с гистерезисом; **дальний мир** — версионированные сводки LOD с правками (§6.5).
- Переносимые постройки — свой `grid_id`, transform 20 Гц, геометрия патчами.
- Античит: сервер проверяет дистанцию, видимость, скорость действий, права; идемпотентные ID действий.

### 5.4. Сохранение
Снимки страниц + журнал транзакций; версия генератора и правил; миграции; восстановление после сбоя без потери
подтверждённых транзакций.

## 6. Рендер (wgpu, один код для Windows и WebGPU)

### 6.1. Основа
- Граф кадра из явных проходов (вход/выход, таймер на проход). Ресурсы создаются **только для включённых режимов**.
- HDR, reverse-Z, MSAA 4× (WebGPU: 1 или 4 сэмпла).
- **Все конвейеры создаются заранее асинхронно** на экране загрузки (по таблице вариантов); смена настройки — без
  компиляции на лету.
- Не больше 2 кадров в работе; ввод читается как можно позже; нативно — VRR, позже Reflex/Anti-Lag 2.

### 6.2. Terrain
- Мешинг **по странице 16³** (бинарный greedy по маскам occupancy), отдельно opaque / cutout / water.
- Формат: **квад-дескриптор 16 байт** (позиция в странице, направление, размер, материал, AO 4×2 бита, оттенок) +
  vertex pulling; без индексного буфера (instanced triangle strip). Цель — ≤ 16 байт/квад.
- **Быстрая оболочка правок**: после правки — немедленная простая геометрия изменённых клеток + маска скрытия старых
  граней; финальный greedy-меш заменяет атомарно (гипотеза H1, §9).
- Арены на GPU (подразбивка большого буфера), стабильные слоты с поколениями.
- **GPU-driven**: таблицы объектов/страниц (transform, bounds, диапазоны), compute: frustum + двухпроходный Hi-Z
  (по реальной глубине, консервативно), компактный список видимого → несколько indirect-вызовов на группу. Нативно —
  `multi_draw_indirect_count` по поддержке. Никаких per-draw bind-ов.

### 6.3. Модели (мобы, игроки, машины, сундуки, предметы)
Меш модели один раз; кадр шлёт только экземпляры (матрицы частей, анимация, вспышка, свечение); отсечение на GPU.
Цель: 1000 мобов ≤ 0,5 мс CPU.

### 6.4. Свет
- **Игровой свет** (уровни MC) — CPU-заливка по страницам, детерминированная (механики зависят).
- **Видимый свет**: RGB-заливка + skylight (видимость неба; цвет неба в шейдере) отдельно от меша; удаление света
  корректно.
- **Отражённый свет (B+)**: мировой кэш проб (DDGI-подобный: irradiance + моменты расстояний), обновление с
  **приоритетом «изменено и видно»**, первая оценка после правки — несколькими лучами; программная трассировка DDA по
  кирпичам (WebGPU); нативно на RTX — ray query как вариант бэкенда.
- Солнце: **каскадные тени со стабилизацией** (неподвижная сетка текселей, солнце шагами, поворот вокруг камеры) +
  **кэш статики** по каскадам (перерисовка только изменённых областей/движущихся объектов).
- Энергия не считается дважды (RGB vs пробы vs прямой) — согласованная модель, описать в `docs/LIGHTING.md`.

### 6.5. Дальний мир (LOD)
- Иерархия сводок **фактического** мира (с правками): страница → группа → регион; правка обновляет только предков.
- Выбор уровня по экранной ошибке (пиксели), гистерезис, без мерцания переходов.
- Защита важных деталей (проёмы, мосты, арки, тонкие башни) — гипотеза H4.
- Дальние сводки приходят с сервера (клиент не грузит точные блоки горизонта).

### 6.6. Небо, атмосфера, облака, вода
- Атмосфера по LUT (семейство Hillaire), одна модель для неба, дымки, LOD, воды и облаков.
- Облака: слоистые (A), объёмные с ограниченным march и своим буфером (B+).
- Вода: Fresnel, поглощение по толщине, преломление полноразмерное, отражение окружения + SSR с fallback, каустика
  из поля волн, пена от потока. **Вода внутри MSAA** (края сглажены).
- Солнце/луна (фазы), звёзды с вращением и мерцанием — повторить вид донора (варианты A/B/C как настройки).
- Свечение блоков/машин (emissive-маски) + bloom умеренный.

### 6.7. Материалы и текстуры
- Texture arrays + таблица материалов; сжатие BC7 (native), ASTC/ETC2 (по поддержке), RGBA8 fallback; mipmaps в
  линейном свете; для alpha — coverage-preserving mips.
- labPBR (нормали, гладкость/F0, эмиссия, POM только вблизи на C/D) — импорт наборов ресурсов локально.
- Листва: **alpha-to-coverage** с MSAA; служебные метки — не в альфе цвета.

### 6.8. Сглаживание
MSAA 4× по умолчанию + фильтрация бликов (нормали → шероховатость) + A2C. SMAA 1× как альтернатива для A.
TAA/DLAA — опция, **выключена по умолчанию**; если включена — с motion vectors объектов и инвалидацией по правкам.

### 6.9. Пост
Экспозиция (гистограмма, медленная адаптация, ручной режим), тонмаппинг, bloom. Без motion blur/DOF/grain по умолчанию.

### 6.10. Авто-качество «Держать 60»
- Никогда не трогает MSAA и тени (вкл/выкл). Рычаги по порядку: «роскошь» выше пресета → SSAO → отражения →
  ближняя дальность → разрешение (не ниже 85 %, только если пользователь разрешил) → детальность дали → дальность.
  Тяжесть теней (разрешение карты, число каскадов) — последней.
- Шаг не чаще раза в 10 с, возврат по измеренной экономии, гистерезис. Не реагирует на одиночный рывок.
- F3: «что снижено и почему».

## 8. Тестирование в облаке (без видеокарты) — обязательно и с первого дня

В облаке нет GPU, поэтому **меряем не миллисекунды, а работу и корректность**. Миллисекунды на железе заказчика —
отдельный этап (§10, M13). Все тесты — в CI (GitHub Actions), зелёный CI — условие слияния в `main`.

### 8.1. Корректность ядра
- Юнит- и property-тесты (proptest): транзакции, версии, журнал, курсоры, публикация только актуальных результатов,
  coalescing не теряет игровых событий, `Unknown` не генерируется синхронно.
- Детерминизм: два прогона одного сценария (и WASM vs native) дают одинаковые хеши состояния на каждом тике.

### 8.2. «Тесты архитектуры» — счётчики работы (главное отличие этого проекта)
Каждый тест фиксирует **обещание стоимости**:
- одна правка блока → мешинг сканирует ≤ 4096 клеток + рамка соседей (по счётчику), загрузка ≤ N КБ;
- 100 000 правок в одной странице → ровно 1 перестройка меша (coalescing);
- кадр в статичной сцене → **0 аллокаций** (считающий аллокатор), 0 компиляций конвейеров, 0 синхронных генераций;
- тик с 10 000 спящих машин → работа тика не растёт относительно 0 машин (± константа);
- цена тика растёт линейно с числом **событий**, не машин (график в отчёте);
- удвоение дальности LOD → число квадов/вызовов растёт ≤ на константу колец, не квадратично;
- правка вдали отражается в LOD-сводке (постройка не исчезает);
- смена цвета лампы не перестраивает меш; смена содержимого сундука не трогает геометрию и свет;
- руды не попадают в клиентский поток до видимости.

### 8.3. Golden-тесты поведения (из донора)
Перенести/переписать тесты донора как эталоны: физика игрока (высота прыжка, скорости, падение, ступеньки, полёт),
крафт (число рецептов, конкретные рецепты), выживание, мобы, PvP, жидкости, Mekanism «тик в тик» (например линия
удвоения: 10 сырого железа → 20 слитков на тике 4632 у донора), логистика, команды и права, генератор (`PROBE_REF`).
Расхождение с донором — только осознанное, с записью в DECISIONS.

### 8.4. Рендер без GPU
- wgpu на программном Vulkan (lavapipe/llvmpipe в CI; на Windows — WARP) рендерит тестовые сцены (из `donor/web/scenes`
  + свои: лес, вода, ночь, пещера, витрина машин, листва, LOD-переход, движущаяся постройка).
- Сравнение с эталонными кадрами: перцептивная метрика (NVIDIA FLIP, порог по сцене); эталоны обновляются только
  осознанно (коммит «обновил эталон X, потому что …»).
- **Мерцание числом**: последовательности кадров при неподвижной/медленной камере (тени, листва, вода, LOD) —
  временная дрожь яркости по маскам ≤ порога; регресс > 20 % — красный CI.
- Проверки инвариантов рендера: нет дыр в LOD (покрытие экрана), Hi-Z не отсекает видимое (сравнение с рендером без
  отсечения — побитово), быстрая оболочка правки + финальный меш = эталон.
- Браузер: сборка WASM + headless Chrome с WebGPU (SwiftShader) открывает сцену и отдаёт кадр — дымовой тест.

### 8.5. Сеть
Безголовый сервер + 2–N ботов-клиентов, внедрение задержки 75±20 мс, потерь 2 %, джиттера: полёт и ходьба без
коррекций, правки с предсказанием и откатом, взрыв на 10 тыс. блоков (размер трафика — в отчёт), переносимая постройка,
восстановление снимком при потере базы, бан/права.

### 8.6. Нагрузка (счётчики, не мс)
Сервер: 32 бота, 5 тыс. сущностей, 10 тыс. машин, 100 тыс. клеток жидкости — счётчики работы на тик, возраст очередей,
трафик на клиента. Время тика в облаке пишется как справочное (не критерий).

### 8.7. Маршрут для железа заказчика
`tools/bench` — детерминированный маршрут (повтор ввода) для запуска заказчиком на RTX 3050 Laptop: кадр p50/p95/p99,
рывки по причинам, GPU по проходам, мерцание, HTML-отчёт, `compare A B`. В облаке — проверка, что маршрут запускается
и выдаёт отчёт.

## 11. Процесс работы агента
- Ветка на этап (`m2-terrain`), маленькие коммиты, PR в `main` при зелёном CI; в описании PR — что сделано, цифры
  счётчиков, что не сделано.
- После каждого этапа — `docs/STATUS.md`, при выборе — `docs/DECISIONS.md`, при провале гипотезы — `docs/RISKS.md`.
- Не переписывать уже принятое без причины. Не плодить параллельные реализации одного (кроме гипотез, которые после
  проверки удаляются).
- «Готово» = зелёный CI + выполненные критерии этапа + обновлённый STATUS. Вид и ощущения окончательно принимает
  заказчик — готовь для него одну сцену и что ожидать.
