Соглашения в этом файле:
- **Пространство вида** (как в Java для руки): +X вправо, +Y вверх, взгляд по −Z, начало — глаз. Единица — блок.
- `Rx/Ry/Rz(θ)` — поворот на θ **градусов** вокруг оси по правилу правой руки (`RotationAxis.POSITIVE_*`).
- Шаги матрицы идут **в порядке вызовов Java**: каждый шаг умножает текущую матрицу справа (`M ← M·X`); вершина модели
  `v_вид = M·v`. То есть последний шаг применяется к вершине первым.
- `sx = +1` для правой руки, `−1` для левой (вторая рука). `s` — прогресс взмаха ∈ [0,1), `e` — «опущенность»
  (`1 − equip`, 0 = поднят полностью).
- Углы взгляда в Java — градусы; **yaw растёт при повороте вправо, pitch > 0 — взгляд вниз**. У нас `cam.pitch > 0` —
  вверх: знак pitch для отставания руки надо перевернуть (§3.2).

## 0. Главное коротко

1. **С предметом в руке рука не рисуется** — только предмет «висит» сам. Рука видна только при пустой главной руке
   (и с картой — не наш случай) [src `renderFirstPersonItem`: `item.isEmpty()` → `renderArmHoldingItem`, иначе только
   `renderItem`].
2. **Плоский предмет и инструмент в первом лице держатся одинаково**: `item/generated` и `item/handheld` имеют одинаковый
   `firstperson_righthand` = поворот (0, −90, 25), сдвиг (1.13, 3.2, 1.13)/16, масштаб 0.68. Различие — только в третьем
   лице [data]. Блоки: (0, 45, 0), 0, 0.40; печь и другие `orientable_with_bottom`: (0, 135, 0) — лицом к игроку [data].
3. **Рука рисуется отдельной проекцией** с FOV **70** (не настройка и не бег), но под водой ×0.857 (= 60) и при смерти
   уменьшается [src `GameRenderer.renderHand` → `getFov(…, false)`]. Перед рукой **очищается глубина** — рука всегда поверх
   мира. Ближняя плоскость 0.05 [src `getBasicProjectionMatrix`].
4. **Подъём после смены слота зависит от скорости атаки предмета**: опускание всегда 3 тика (1 → 0.6 → 0.2 → 0), затем
   цель `кулдаун³`: рука/блок поднимаются за 4 тика (всего 7 тиков = 0.35 с), меч — всего 14 тиков (0.7 с), кирка —
   18 тиков (0.9 с), топор — 26 тиков (1.3 с) [src `updateHeldItems` + `PlayerEntity.tick` сбрасывает кулдаун при смене
   **типа** предмета; вывод — таблица §10.3].
5. **«Тот же стек» = тот же объект или `ItemStack.areEqual` (тип + количество + компоненты)**. Поэтому изменение прочности
   инструмента (после каждого блока) и подбор предметов в держимый стек дают быстрое «опустить-поднять» (6 тиков), а
   ставление блока и выброс Q (меняют количество «на месте») — нет (ставление даёт свой явный `resetEquipProgress`).
   Метода `shouldSkipHandAnimationOnSwap` в `HeldItemRenderer` 1.21.1 **нет** — сравнение только через `areEqual`
   [src]; в какой версии он появился — [не проверено].
6. **Освещение руки — по миру, а не по экрану**: нормали руки переводятся в мировую ориентацию, свет — две фиксированные
   мировые «лампы» (0.4 + 0.6·Σ) и яркость lightmap в блоке глаз. Посмотрел вверх/вниз — затенение граней предмета
   меняется [src `renderHand` + `MatrixStack.multiplyPositionMatrix` + `light.glsl`].
7. **Отставание за мышью**: `renderYaw/Pitch` догоняют взгляд ×0.5 за тик, рука поворачивается на
   `(взгляд_сейчас − lerp(last, render))·0.1°`. При ровном повороте ω °/тик отставание взгляда = 2ω, руки — 0.2ω°
   [src `ClientPlayerEntity.tickNewAi`, `HeldItemRenderer.renderItem`; вывод].
8. **Еда**: за ~3–4 тика предмет уходит к центру-низу экрана (`h = 1 − g^27`), после 20 % времени трясётся `|cos(f·π/4)|·0.1`
   — 5 раз в секунду; одновременно `resetEquipProgress` в начале — еда приходит снизу. Отпустил ПКМ — предмет мгновенно
   возвращается [src `applyEatOrDrinkTransformation`, `doItemUse`].
9. **Экструзия спрайта**: две грани 16×16 (толщина 1/16 модели, z 7.5…8.5) + полоски на краях непрозрачных пикселей
   (α = 0 — прозрачный), полоски одной стороны в одном ряду/столбце **сливаются в одну** от мин. до макс. края
   [src `ItemModelGenerator`].
10. **Покачивание руки** — тот же `bobView`, что у камеры, применён к матрице руки; амплитуда одинакова при ходьбе и беге
    (`strideDistance ≤ 0.1`), меняется только темп [src].

## 1. Порядок операций

### 1.1. Тик клиента (`MinecraftClient.tick`) — что касается руки [src]

1. `itemUseCooldown−−`; луч `updateCrosshairTarget(1.0)`; `interactionManager.tick()` (ASP-04/05).
2. `handleInputEvents()` (если окно закрыто):
   - клавиши 1–9 → `selectedSlot` (колесо меняет слот ещё раньше, в событии мыши — ASP-08 §5);
   - Q → `dropSelectedItem` (стек уменьшается **на месте**) → взмах, если что-то выпало;
   - ЛКМ → `doAttack`: по блоку — `attackBlock` + взмах; в воздух (MISS) — `attackCooldown = 10`,
     **`resetLastAttackedTicks()`** + взмах;
   - ПКМ → `doItemUse`: успех по блоку (SUCCESS) — взмах, и если стек не пуст и `count` изменился —
     **`resetEquipProgress(hand)`**; успех предмета «в воздух» (еда — CONSUME) — взмах только если SUCCESS, но
     **`resetEquipProgress` всегда** (ASP-05 §1.2);
   - удержание ЛКМ → `handleBlockBreaking`: взмах каждый тик удержания (ASP-04 §8); отпускание → `cancelBlockBreaking`
     → **`resetLastAttackedTicks()`**.
3. `attackCooldown−−`.
4. **`gameRenderer.tick()`** → `updateFovMultiplier`, `camera.updateEyeHeight`, **`heldItemRenderer.updateHeldItems()`**
   (§2.1). Здесь кулдаун атаки берётся **до** `lastAttackedTicks++` этого тика, поэтому формула с `+1.0` (§2.2).
5. `world.tickEntities()` → тик игрока (`PlayerEntity.tick`):
   1. `LivingEntity.tick` → `Entity.tick` → `baseTick`: **`lastHandSwingProgress = handSwingProgress`**;
   2. `tickActiveItemStack` → `tickItemStackUsage`: эффекты еды (§4.4), **`itemUseTimeLeft−−`**, на 0 — съедено;
   3. `tickMovement` → `tickNewAi` → **`tickHandSwing`** (ASP-04 §8) и **`lastRenderYaw/Pitch ← renderYaw/Pitch;
      renderPitch += (pitch − renderPitch)·0.5; renderYaw += (yaw − renderYaw)·0.5`** (только если игрок — камера);
      потом движение; после него **`strideDistance += (min(0.1, |v_гор|) − stride)·0.4`** (0 в воздухе), а `Entity.move`
      копит `horizontalSpeed += |Δгор|·0.6` (CAM-03, ASP-02);
   4. **`lastAttackedTicks++`**; если главный стек не `areEqual` с прошлым `selectedItem`: если **другой тип** —
      `resetLastAttackedTicks()`; `selectedItem = копия`.

Следствие для нашего тика (`game.rs`: `tick_use → tick_player → tick_world`): обновление руки (`Held::tick`, §2.1) стоит
**между `tick_use` и `tick_player`**; взмах, `renderYaw`, таймер еды, `lastAttackedTicks` — внутри `tick_player` в
порядке выше.

### 1.2. Кадр (`GameRenderer.renderWorld` → `renderHand`) [src]

1. Мир рисуется с проекцией `P(FOV_мира) · Tilt · Bob` (наклон от удара и покачивание — в проекции).
2. **`RenderSystem.clear(DEPTH)`** — глубина мира стирается.
3. `renderHand(camera, tickDelta, R_камеры)`, если не панорама:
   1. своя проекция `P(getFov(…, false), aspect, 0.05, far)` (§5.1);
   2. стек матриц: `R_камеры⁻¹`, затем `tiltViewWhenHurt`, затем `bobView` (если опция «покачивание» вкл.);
      model-view шейдера = `R_камеры` → итог по позиции = `Tilt · Bob · …` в пространстве вида, а нормали — в мировой
      ориентации (§5.3);
   3. рука рисуется, если: вид от первого лица, игрок не спит, HUD не скрыт (F1), не наблюдатель;
   4. `heldItemRenderer.renderItem(tickDelta, …, light = свет в блоке глаз)` (§3);
   5. после руки — оверлеи (вода, огонь, «в стене»), потом GUI (виньетка поверх руки).

## 2. Состояние руки и его обновление в тике

### 2.1. `updateHeldItems` — опускание и подъём [src `HeldItemRenderer.updateHeldItems`, `resetEquipProgress`]

Состояние рендерера: `mainHand`, `offHand` — **какие стеки сейчас нарисованы** (могут отставать от инвентаря);
`equipProgressMainHand/OffHand` и их `prev…` (f32, 1 = поднят).

Каждый тик:
1. `prev ← equip` (для обеих рук).
2. `real = стек в главной руке` (вторая — аналогично). Если `ItemStack.areEqual(mainHand, real)` — `mainHand ← real`
   (принять новый объект без анимации).
   `areEqual`: тот же объект **или** (равное количество **и** тот же тип **и** равные компоненты); пустые стеки равны
   [src `ItemStack.areEqual/areItemsAndComponentsEqual`; `getItem()` пустого = AIR].
3. Верхом — `equip −= 0.4` с зажимом (не наш случай). Иначе:
   - главная: цель = `кулдаун³`, если `mainHand` — тот же объект, что `real` (то есть после шага 2), иначе **0**;
     `equip += clamp(цель − equip, −0.4, 0.4)`;
   - вторая: цель = 1 или 0 (без кулдауна).
4. Если `equip < 0.1` — `mainHand ← real` (подмена нарисованного стека «внизу»).

`resetEquipProgress(hand)` ставит `equip = 0` **без** `prev` → в кадре предмет **мгновенно** внизу, затем
`0 → 0.4 → 0.8 → 1.0` (ASP-05 §2.6).

Разбор случаев [src + вывод; последовательности `equip` по тикам]:

| Событие | Что видно | equip по тикам |
|---|---|---|
| Смена слота на **другой тип** (или на пустую руку) | старый уходит вниз 3 тика, новый поднимается по `кулдаун³` (кулдаун сброшен `PlayerEntity.tick`) | 0.6, 0.2, 0 (подмена), далее по скорости атаки — §10.3 |
| Смена на слот с **равным** стеком (64 земли ↔ 64 земли; две целые новые кирки) | ничего | 1, 1, … |
| Смена на тот же тип, но другое количество/прочность | быстрое «опустить-поднять», кулдаун не сбрасывается | 0.6, 0.2, 0, 0.4, 0.8, 1.0 |
| Прочность инструмента изменилась (после каждого сломанного блока) | то же быстрое «нырок» на 6 тиков | 0.6, 0.2, 0, 0.4, 0.8, 1.0 — см. §7 п. 1 |
| Подобрал предметы **в держимый стек** | то же | 0.6, 0.2, 0, 0.4, 0.8, 1.0 |
| Поставил блок, стек не опустел | явный `resetEquipProgress`: мгновенно вниз, подъём 3 тика | 0 → 0.4, 0.8, 1.0 |
| Поставил **последний** блок | рука появляется **сразу**, без подъёма (стек опустел на месте → тот же объект) | 1, 1, … |
| Q / Ctrl+Q | только взмах, без «нырка»; если стек кончился — пустая рука появляется сразу (тот же, теперь пустой, объект) | 1, 1, … |
| Начал есть | `resetEquipProgress` → еда приходит снизу, одновременно к рту | 0 → 0.4, 0.8, 1.0 |
| Доел последний | рука появляется сразу | 1, 1, … |
| Клик в воздух (MISS), отпускание ЛКМ при ломании | «нырок» по `кулдаун³` (§2.2) | рука: 0.6, 0.2, 0.216, 0.512, 0.912, 1 |

Почему подбор и прочность «ныряют», а ставление и Q — нет: на клиенте Java ставление (`BlockItem.place`) и выброс
(`PlayerInventory.dropSelectedItem` → `split`) **меняют тот же объект**, а прочность и подбор приходят от сервера новым
объектом (`onScreenHandlerSlotUpdate` → `setStackInSlot`) — и сравнение уже по значению [src]. Прочность на клиенте вообще
не предсказывается (`ItemStack.damage` только на `ServerWorld`) [src]. **Для нас (без сервера) это надо эмулировать явно**
(§11.1: «идентичность» стека).

Быстрая прокрутка колесом через несколько слотов: подмена происходит в тик, когда `equip < 0.1`, — показывается
только старый предмет вниз и тот, что выбран в момент подмены (промежуточные не видны). Возврат на исходный слот, пока
`equip ≥ 0.1`, — старый предмет просто поднимается обратно (шаг 2 принимает его) [вывод].

### 2.2. Перезарядка атаки и опускание предмета (TOOL-04) [src `PlayerEntity.getAttackCooldownProgress`, `tick`]

- `T = 20 / attack_speed` тиков; `кулдаун(base) = clamp((lastAttackedTicks + base) / T, 0, 1)`; рука берёт `base = 1.0`.
- `attack_speed`: рука и все неоружейные предметы 4.0 (T = 5); меч 1.6 (12.5); кирки 1.2 (16.67); лопаты 1.0 (20);
  топоры дер./кам. 0.8 (25), жел. 0.9 (22.2); мотыги 1.0/2.0/3.0 [src через каталог TOOL-03].
- Сброс `lastAttackedTicks = 0`: клик в воздух (`doAttack` MISS), `cancelBlockBreaking` (если шло ломание), удар по
  сущности, смена **типа** предмета в главной руке (`PlayerEntity.tick`). Клик по блоку и само ломание — **не** сбрасывают.
- Вторая рука от кулдауна не зависит.
- Атрибут скорости атаки на клиенте обновляется сервером (модификаторы предмета) — в одиночной игре задержка ~1 тик
  [не проверено]; у нас — сразу.

### 2.3. Взмах [src `LivingEntity.swingHand/tickHandSwing/getHandSwingProgress`; подробно — ASP-04 §8]

- `D = 6` тиков. `swingHand(hand)`: если не машет, или `ticks ≥ D/2 = 3`, или `ticks < 0` → `ticks = −1`,
  `swinging = true`, **`preferredHand = hand`** (машет только эта рука).
- Тик: `last = progress` (в `baseTick`); если машет — `ticks++`, на `ticks ≥ 6` → `ticks = 0`, конец; `progress = ticks/6`.
- Кадр: `s = last + Δ·td`, `Δ = progress − last`, при `Δ < 0` → `Δ += 1`.
- Удержание ЛКМ на блоке: `progress` по тикам `0, 1/6, 2/6, 3/6, 0, 1/6, …` — дуга 0→½ за 3 тика и быстрый «довод»
  ½→1 (≡ 0) за 1 тик, период **4 тика**. Одиночный клик — `0…5/6, 0` за **6 тиков**.

### 2.4. Отставание за мышью [src `ClientPlayerEntity.tickNewAi`, `getYaw/getPitch(float)`; `HeldItemRenderer.renderItem`]

- В тике (только когда игрок — камера): `lastRender ← render; render += (взгляд − render)·0.5` (yaw и pitch, f32).
- В кадре: `ΔP = pitch_сейчас − lerp(td, lastRenderPitch, renderPitch)`, `ΔY = yaw_сейчас − lerp(td, lastRenderYaw,
  renderYaw)`; `pitch_сейчас/yaw_сейчас` у `ClientPlayerEntity` **без интерполяции** (мышь меняет их каждый кадр).
- Поворот руки: `Rx(ΔP·0.1) · Ry(ΔY·0.1)` (в этом порядке, до всего остального).
- Ровный поворот ω °/тик → `ΔY = 2ω` при любом `td` (проверено численно) → рука на `0.2ω°`. Пример: 180° за 0.5 с
  (18 °/тик) → рука отстаёт на 3.6°; 90 °/с (4.5 °/тик) → 0.9°. После остановки разница уменьшается вдвое за тик →
  ~0.2 с [вывод].
- Yaw в Java **не заворачивается** в [0, 360) — разница непрерывна. У нас при заворачивании угла получится прыжок на 360°
  → рука дёрнется на 36° (§6).

### 2.5. Использование (еда) [src `LivingEntity.setCurrentHand`, `tickItemStackUsage`, `Item.getMaxUseTime`]

- Начало: `itemUseTimeLeft = maxUseTime` (еда: `eat_seconds·20` = **32**, сушёная ламинария 16 [не проверено]).
  В том же тике `tickItemStackUsage` уменьшит до 31 → первый кадр после тика уже в движении.
- Каждый тик: эффекты (§4.4), `itemUseTimeLeft−−`; на 0 — `consumeItem` (стек −1 **на месте**, `clearActiveItem`).
- Анимация еды идёт, пока `isUsingItem && itemUseTimeLeft > 0 && activeHand == эта рука`.
- Смена слота во время еды прерывает использование (ASP-08 §5). Удержание ПКМ после съедания → следующая порция
  с новым `resetEquipProgress`.

## 3. Матрица руки в кадре — по шагам

### 3.1. Проекция [src `GameRenderer.renderHand`, `getFov`, `getBasicProjectionMatrix`]

`P_рука = perspective(fovY, W/H, near = 0.05, far = viewDistance·4)` (вертикальный FOV, как у мира), где
- `fovY = 70`;
- под водой/в лаве (по положению камеры): `× lerp(fovEffectScale, 1, 0.85714287)` → **60** при «эффектах FOV» 100 %;
- при смерти: `f = min(deathTime + td, 20)`, `fovY /= (1 − 500/(f + 500))·2 + 1` → до **65** на 20-м тике;
- **не** входят: настройка FOV, множитель бега/полёта, тошнота, зум.

### 3.2. Общая часть для обеих рук

```
M = Tilt · Bob · Lag
Tilt = (наклон от удара, ASP-12: Ry(−yawУдара)·Rz(−f·14·сила)·Ry(yawУдара), f = sin(((hurtTime−td)/10)⁴·π))
Bob  = T(sin(gπ)·h·0.5, −|cos(gπ)·h|, 0) · Rz(sin(gπ)·h·3) · Rx(|cos(gπ − 0.2)·h|·5)      — если опция вкл.
       g = −(hs + (hs − hs_prev)·td)   ← экстраполяция, не lerp! [src bobView]
       h = lerp(td, stride_prev, stride)
Lag  = Rx(ΔP·0.1) · Ry(ΔY·0.1)          (Java-знаки: pitch > 0 вниз; у нас ΔP_java = −ΔP_наш)
```
`hs` — `horizontalSpeed`, `stride` — `strideDistance` (§1.1 п. 5.3). Те же Tilt и Bob стоят в проекции мира — мир и рука
качаются одним движением, но рука близко (0.6–1.2 блока) и её сдвиг на экране заметно больше.

Дальше для каждой руки (`main` всегда, `off` — если есть предмет) со своим `s` (у машущей руки — §2.3, у другой 0) и
`e = 1 − lerp(td, prevEquip, equip)`. Пустая вторая рука не рисуется.

## 4. Модели

### 4.1. Экструзия плоского предмета [src `ItemModelGenerator.create/addLayerElements/addSubComponents/getFrames/buildCube`]

Для каждого слоя спрайта (у нас — один `layer0`):
1. **Лицо и изнанка**: элемент от (0, 0, 7.5) до (16, 16, 8.5) (модельные единицы 1/16) с двумя гранями: SOUTH (+Z, UV
   0,0→16,16) и NORTH (−Z, UV **16,0→0,16** — зеркально, чтобы с изнанки картинка читалась так же). Квад всегда
   **полный 16×16**, прозрачные тексели отбрасываются в шейдере (α < 0.1). Толщина = 1/16 размера предмета; в руке
   ×0.68 → 0.0425 блока.
2. **Края**: для каждого непрозрачного пикселя (x, y) (прозрачный = **α == 0** ровно [src `SpriteContents.isPixelTransparent`];
   полупрозрачный считается непрозрачным) и каждой из 4 сторон: если сосед в эту сторону прозрачный или за краем —
   добавить край. Стороны: UP (сосед y−1), DOWN (y+1), LEFT (x−1), RIGHT (x+1).
3. **Слияние**: края копятся во «фреймы» `(сторона, уровень)`, уровень = ряд y для UP/DOWN и столбец x для LEFT/RIGHT;
   новый край того же фрейма лишь расширяет `[min, max]` вдоль ряда/столбца — **даже через разрывы**. Итог — одна полоска
   на (сторону, ряд/столбец).
4. Полоска = вырожденный элемент толщиной 7.5…8.5 по Z, с одной гранью; текстура — ряд/столбец краевых пикселей
   (UV шириной 1 px). Модельная Y перевёрнута относительно текстурной (`y_модели = 16 − y_текстуры`).
5. Пиксель → 16/ширина спрайта единиц (для 16×16 — 1:1). Масштаб спрайта не меняет толщину (всегда 7.5…8.5).

Мелочь [src][вывод, глазами не сверено]: стороны LEFT/RIGHT в Java получают направления **EAST/WEST наоборот**
(`LEFT(Direction.EAST, −1, 0)`, `RIGHT(Direction.WEST, 1, 0)`): нормаль и обход смотрят **внутрь** предмета, UP/DOWN —
наружу. С отсечением задних граней это даёт «вид на дальнюю стенку сквозь ближнюю», при толщине 1 px не различимо.
Предлагаю делать все полоски наружу и с отсечением [решение] — разница в цвете полоски на 1 px.

Эталоны счёта (2 + полоски) [вывод, пересказ алгоритма]: весь 16×16 → 4 полоски (6 квадов); один пиксель → 4 (6);
квадрат 4×4 → 4 (6); диагональ `x + y = 15` (рукоять) → 64 (66); ряд 4 с пикселями x = 2 и x = 10 → UP 2…10 и DOWN 2…10
одной полоской каждая + 4 боковые = 6 (8).

Цвет: квады с `tintindex` красятся по `ItemColors` (трава, листва — **фиксированный цвет по умолчанию**, не биом: цвет
блока берётся с `world = null`) [src `ItemColors`; сами значения по умолчанию — не проверено].

## 5. Отрисовка

### 5.1. Проекция и глубина
§3.1. Глубина мира перед рукой **стирается**; внутри прохода руки тест глубины включён (предмет и рука закрывают сами
себя правильно). Туман к руке почти не применяется (расстояние < 1.5 блока).

### 5.2. Порядок на экране
Мир → вода/частицы → **рука** → оверлеи (под водой, огонь) → GUI (виньетка, хотбар) поверх руки. Пост-эффекты Java
(`postProcessor`) — после всего мира, рука в обычной игре в них не участвует.

### 5.3. Освещение руки [src `renderHand`, `MatrixStack.multiplyPositionMatrix`, `WorldRenderer.render` 936–940, `DiffuseLighting`, `light.glsl`, `rendertype_entity_cutout`, `EntityRenderer.getLight`]

- Позиция идёт в вид (`R_кам · R_кам⁻¹ · …`), но **нормали — в мировой ориентации** (стек начинается с `R_кам⁻¹`, и
  `multiplyPositionMatrix` с ортонормальной матрицей обновляет и матрицу нормалей).
- Рассеянный свет сущностей (Верхний мир, `disableForLevel`): две лампы
  `L0 = norm(0.2, 1, −0.7)`, `L1 = norm(−0.2, 1, 0.7)` (мировые оси Java: +X восток, +Z юг):
  `k = min(1, (max(0, L0·N) + max(0, L1·N))·0.6 + 0.4)`.
  Эталоны: верх 1.0, низ 0.4, +X 0.497, ±Z 0.740, (1,0,1) 0.571, (−1,0,1) 0.709 [вывод].
- Яркость: `lightmap(blockLight, skyLight)` **в блоке глаз** (`floor(позиция глаз с td)`); горит — блочный свет 15.
- Итог фрагмента: `текстура × k × lightmap` (α < 0.1 — отбросить).
- Ощущение: в пещере и ночью рука темнеет вместе с миром; посмотрел вертикально вниз — бывшая «верхняя» грань блока
  в руке становится «боковой» по миру и темнеет до 0.5–0.7; поворот по yaw чуть меняет боковые грани.

## 6. Граничные случаи и мелочи

1. Предмет в руке — без руки; пустая рука — без предмета; пустая вторая рука — ничего.
2. Смена между **равными** стеками — нет анимации; между тем же типом с другим количеством/прочностью — быстрый нырок
   без сброса кулдауна; между разными типами — нырок и медленный подъём по кулдауну (инструменты).
3. После каждого сломанного блока инструмент «ныряет» (прочность) — §7 п. 1. Рукой и блоком — нет.
4. Ставление: мгновенно вниз и подъём 3 тика; при удержании ПКМ (раз в 4 тика) — пульс: `0→0.4→0.8→1.0→1.0→(сброс)`;
   плюс взмах на каждый блок. Последний блок — рука сразу.
5. Отпускание ЛКМ во время ломания — нырок по кулдауну (кирка поднимается ~0.8 с). Клик в воздух — то же + взмах.
6. Еда: начало с нырком снизу, отпускание — мгновенный возврат; повтор при удержании — снова нырок.
7. Окно инвентаря открыто: тик рендерера руки продолжается (видно за полупрозрачным фоном), взмахов нет. Пауза (Esc в
   одиночной) — всё замирает [src: `gameRenderer.tick` только `!paused`].
8. F1 — руки нет; третье лицо — руки нет; опция «покачивание» выкл. — нет Bob ни у камеры, ни у руки.
9. Под водой рука **мгновенно** крупнее (FOV 60) при погружении глаз и обратно при выныривании — множитель без
   сглаживания (у мира сглаживается только бег).
10. Узкое окно (4:3 и уже) — головка инструмента и часть блока уходят за правый край: размер руки привязан к высоте экрана.
11. Бег не меняет руку (FOV мира растёт, руки — нет). Присед не меняет положение руки (только покачивание медленнее).
12. В прыжке покачивание гаснет: `stride` → 0 с множителем 0.6 за тик (~5 тиков).
13. Резкий скачок yaw (телепорт, респаун, заворачивание угла у нас) даёт рывок руки на 0.1 скачка — у нас сбрасывать
    `render_yaw = yaw` при телепорте и не заворачивать yaw (или брать разницу в (−180, 180]) [решение].
14. `Δ < 0 → +1` во взмахе: при перезапуске на половине дуга идёт ½→1, а не назад — кажется «щелчком» возврата.
15. Порядок в тике: равенство стеков проверяется **до** тика игрока — смена слота в тике T: в этом же тике цель 0
    (опускание началось), а кулдаун сбросится только в тике игрока T.

## 7. Чего нет в исходнике / не ясно

1. **Нырок инструмента после каждого блока.** По коду 1.21.1 — да (прочность приходит новым стеком, `areEqual` ложно).
   Сходится с тем, что Fabric API даёт моду хук `allowComponentsUpdateAnimation` «чтобы отключить ванильную анимацию при
   изменении компонентов» [не проверено: документация Fabric по памяти]. Живую игру не запускали. Предлагаю повторить
   (решение «причуды повторяем») и проверить глазами по сценарию §8 п. 7 — это то, о чём спрашивал ASP-04 §13 п. 2.
2. **Свет руки в нашем движке.** В Java нет солнечных теней: рука в тени дерева не темнеет (только skyLight < 15 под
   листвой). У нас солнечные тени и HDR: если взять только «небесный уровень», рука будет светиться в тени. Нужна
   адаптация (§9.3) — решение «Свет и материалы».
3. **Скин.** Свой простой 64×64 по раскладке §4.3; широкая рука 4×12×4 [решение]. Рукав — по желанию позже.
4. **Сундук в руке** — у Java особая модель сущности; для нашего блочного сундука предлагаю поворот печи (135), чтобы
   защёлка смотрела в ту же сторону [решение, вывод из сравнения gui-трансформов, глазами не сверено].
5. **Задержка сети**: прочность/атрибут скорости приходят на 1 тик позже; у нас — в том же тике. Разница 50 мс,
   повторять не нужно.
6. **Значения по умолчанию цвета травы/листвы для предметов** и `eat_seconds` у отдельных продуктов — не читал
   (`GrassColors`, `FoodComponents`); числа еды — ASP-12.
7. Цвет `lightmap` (день/ночь, гамма, мерцание) — ASP-14.
8. Направленность боковых полосок экструзии (§4.1) — мелочь, делаем наружу.

## 8. Сценарий проверки человеком

ПК, 16:9, FOV мира по умолчанию, «покачивание» вкл. Ожидания по времени — с допуском ±1 тик (50 мс).

1. **Пустая рука, стою.** Рука выходит из нижнего правого края, кулак примерно на ¾ ширины и ¾ высоты экрана (сверху);
   видны перед и внешний бок руки. Предметов нет.
2. **Клик ЛКМ в воздух.** Кулак бьёт к прицелу (чуть вверх-влево), опускается и возвращается за **0.3 с**; заодно вся
   рука слегка «приседает» и встаёт (~0.3 с).
3. **Держу ЛКМ на земле рукой.** Короткие удары **5 в секунду** (каждые 0.2 с), блок ломается; после поломки рука
   **не** ныряет.
4. **Слот 1 → 2 (земля).** Рука уходит вниз за 0.15 с, блок поднимается за ~0.2 с. Блок в правом нижнем углу, низом
   за краем экрана, видно верх и большую левую грань.
5. **Слот 2 → 3 (деревянная кирка).** Блок уходит вниз за 0.15 с, кирка поднимается **медленно, с разгоном, ~0.75 с**
   (сначала почти не видно движения, потом быстрее).
   Кирка: рукоять из нижнего края, головка у правого края примерно на 40 % высоты сверху; видно плоскость кирки под углом
   и её толщину на правом крае.
6. **Две полные стопки земли (64 и 64) в слотах 4 и 5**: переключаю — **никакой** анимации. Стопки 64 и 30 — быстрый
   нырок 0.3 с.
7. **Копаю камень киркой (держу ЛКМ).** Взмах каждые 0.2 с: головка идёт дугой вниз-вперёд к точке чуть ниже-левее
   прицела и обратно. **После каждого сломанного блока кирка быстро ныряет и встаёт (0.3 с)** — сверить с памятью о
   Minecraft (§7 п. 1).
8. **Отпускаю ЛКМ посреди блока с киркой** — кирка падает вниз и медленно поднимается (~0.8 с).
9. **Ставлю землю ПКМ.** Каждый блок: блок в руке мгновенно проседает и поднимается за 0.15 с + взмах. Держу ПКМ — пульс
   5 раз в секунду. Ставлю **последний** блок — рука появляется сразу, без подъёма.
10. **Иду по ровному.** Рука качается в такт шагам (~2.6 шага/с): дуга вбок и вниз; бегу — темп ~3.4/с, размах тот же;
    приседаю — медленно и меньше; прыгаю — качание гаснет за ~0.25 с; встал — затихает. Выключаю «покачивание» — рука
    неподвижна.
11. **Поворот мышью.** Резко вправо — рука отстаёт на пару градусов влево и догоняет за ~0.2 с; резко вверх — отстаёт вниз.
    Медленный ровный поворот — маленькое постоянное отставание. Включаю бег — мир «растягивается», **рука не меняет
    размер**.
12. **Ем яблоко (здоровье не полное).** Яблоко за ~0.2 с уходит к центру-низу экрана (чуть левее центра), через ~0.35 с
    начинает подпрыгивать **5 раз в секунду**, сыплются крошки и звук; через **1.6 с** съедено. Держу ПКМ — следующее
    снова «приходит снизу» к рту. Отпускаю раньше — яблоко **мгновенно** на обычном месте.
13. **Ныряю.** Как только глаза под водой — рука/предмет **сразу** чуть крупнее; вынырнул — обратно.
14. **Ночь / пещера.** Рука темнеет вместе с окружением; смотрю вертикально вверх и вниз — оттенки граней блока в руке
    немного меняются.
15. **Сужаю окно до 4:3** — головка кирки уходит за правый край; F1 — руки нет.

### 9.3. Набросок прохода на WebGL2

Сейчас кадр: тени → небо → непрозрачное (MSAA) → вырезка → `resolveScene` → вода в `targets.resolve` → `post.render`
(SSAO и туман читают `targets.depth`). Очистить общую глубину нельзя — пост её читает. Предлагаю:

1. После воды переиспользовать **`targets.msaa`** (после `resolveScene` он в этом кадре свободен; без MSAA — отдельный
   FBO): `clearColor(0,0,0,0)`, `clear(COLOR | DEPTH)`.
2. Нарисовать руку/предмет(ы): `DEPTH_TEST` вкл., `LEQUAL`, `depthMask(true)`, отсечение задних граней (полоски наружу),
   без смешивания (вырезка α < 0.1).
3. `blitFramebuffer` в новую текстуру **`targets.hand`** (RGBA16F, тот же формат) — разрешение MSAA.
4. В `post.js` после SSAO и тумана, **до** bloom/экспозиции/тонмаппинга/цветокоррекции/виньетки:
   `c = c·(1 − hand.a) + hand.rgb` (premultiplied — фон очищен нулём). Так у руки та же экспозиция и тонмаппинг, нет
   SSAO/тумана мира за ней, а виньетка ложится поверх — как GUI в Java. Это изменение контракта пост-обработки
   (владелец «Свет и материалы») [решение].
   Запасной простой вариант для среза 1: рисовать руку после поста прямо в экран, с тонмаппингом в шейдере руки; минусы —
   нет MSAA (canvas `antialias: false`), нет виньетки поверх.

Матрицы на кадр (JS):
```js
// hv — снимок из Rust; td — loop.alpha; yawNow/pitchNow — текущий взгляд (рад, наши знаки)
const fov = 70 * (eyeInWater ? 0.85714287 : 1) / deathZoom(hv, td);            // §3.1
const P = m4.persp(fov * Math.PI / 180, canvas.width / canvas.height, 0.05, 16);
const base = mul(tilt(hv, td), bob(hv, td), lag(hv, td, yawNow, pitchNow));     // §3.2 (pitch: знак наоборот)
for (const hand of [MAIN, OFF]) {
  const M = mul(base, wasm.hand_pose(hand, td));   // §3.3–3.6 до T(−0.5) включительно
  const N = mat3(mul(invCamRot, M));               // нормали в мир — для двух ламп §5.3
  draw(hand, P, M, N);
}
```
Шейдер руки (суть): `gl_Position = uP * uM * vec4(pos, 1)`; `n = normalize(uN * normal)`;
`k = min(1, (max(0, dot(L0, n)) + max(0, dot(L1, n))) * 0.6 + 0.4)`; `color = tex.rgb * k * uEyeLight`;
`if (tex.a < 0.1) discard`. `uEyeLight` — яркость в точке глаз в шкале HDR мира: до ASP-14 — `небо(время суток) ×
видимость солнца из карты теней в точке глаз (1 выборка PCF)` + рассеянное небо; с ASP-14 — уровни skyLight/blockLight
в блоке глаз через ту же кривую, что у мира [решение «Свет и материалы»].

Меши: рука — 1 кубоид (24 вершины, UV скина); предмет «плоский» — 2 квада 16×16 + полоски (кэш по номеру предмета,
строится при загрузке из альфа-маски — функция `extrude` в Rust, §11.3); «блок» — 6 граней куба со слоями атласа блока и
его оттенком (без AO). Всё — несколько десятков квадов, один-два вызова отрисовки.

### 11.1. Состояние и тик
```rust
/// Стек с «идентичностью»: id меняется, когда Java выдала бы НОВЫЙ объект (подбор в стек, изменение прочности,
/// замена из окна), и не меняется при правке «на месте» (ставление −1, Q, доел −1). Сравнение руки — как areEqual.
#[derive(Clone)]
pub struct Stack { pub item: u16, pub count: u8, pub damage: u16, pub id: u32 }
fn same_value(a: &Stack, b: &Stack) -> bool {
    (a.is_empty() && b.is_empty()) || (a.count == b.count && a.item == b.item && a.damage == b.damage)
}
fn are_equal(a: &Stack, b: &Stack) -> bool { a.id == b.id || same_value(a, b) }   // рука: объект или значение

pub struct Held { pub shown: [Stack; 2], pub equip: [f32; 2], pub prev: [f32; 2] }

impl Held {
    pub fn reset(&mut self, hand: usize) { self.equip[hand] = 0.0; }          // resetEquipProgress: prev не трогаем
    /// Между tick_use и tick_player. cooldown = attack_cooldown(1.0) ДО lastAttackedTicks++ этого тика.
    pub fn tick(&mut self, real: [&Stack; 2], cooldown: f32) {
        self.prev = self.equip;
        for h in 0..2 {
            let same = are_equal(&self.shown[h], real[h]);
            if same { self.shown[h] = real[h].clone(); }
            let target = match (same, h) { (false, _) => 0.0, (true, 0) => cooldown * cooldown * cooldown, _ => 1.0 };
            self.equip[h] += (target - self.equip[h]).clamp(-0.4, 0.4);
            if self.equip[h] < 0.1 { self.shown[h] = real[h].clone(); }
        }
    }
}

pub struct Player { last_attacked: i32, selected: Stack, swing: Swing, ryaw: [f32; 2], rpitch: [f32; 2], /* … */ }
impl Player {
    fn attack_cooldown(&self, base: f32, attack_speed: f32) -> f32 {
        ((self.last_attacked as f32 + base) / (20.0 / attack_speed)).clamp(0.0, 1.0)
    }
    /// Внутри tick_player, после движения (порядок §1.1 п. 5).
    fn tick_attack_and_selected(&mut self, main: &Stack) {
        self.last_attacked += 1;
        if !same_value(&self.selected, main) {          // в Java selectedItem — копия: сравнение только по значению
            if self.selected.item != main.item || self.selected.is_empty() != main.is_empty() { self.last_attacked = 0; }
            self.selected = main.clone();
        }
    }
    fn tick_render_angles(&mut self, yaw: f32, pitch: f32) {    // в tick_new_ai, градусы Java, yaw без заворачивания
        self.ryaw = [self.ryaw[1], self.ryaw[1] + (yaw - self.ryaw[1]) * 0.5];
        self.rpitch = [self.rpitch[1], self.rpitch[1] + (pitch - self.rpitch[1]) * 0.5];
    }
}
```

### 11.2. Матрица (без зависимостей, `[f32; 16]` по столбцам, как `m4` в JS)

```rust
pub struct Disp { rot: [f32; 3], tr: [f32; 3], sc: f32 }        // §3.6; tr в 1/16
pub const FLAT: Disp = Disp { rot: [0.0, -90.0, 25.0], tr: [1.13, 3.2, 1.13], sc: 0.68 };
pub const BLOCK: Disp = Disp { rot: [0.0, 45.0, 0.0], tr: [0.0; 3], sc: 0.40 };
pub const FURNACE: Disp = Disp { rot: [0.0, 135.0, 0.0], tr: [0.0; 3], sc: 0.40 };

/// Предмет: шаги 1–8 §3.3 (s — взмах, e — опущенность, sx = ±1).
pub fn item_pose(s: f32, e: f32, sx: f32, d: &Disp, left: bool) -> M4 {
    let r = s.sqrt(); let pi = std::f32::consts::PI;
    let mut m = M4::translate(sx * -0.4 * (r * pi).sin(), 0.2 * (2.0 * r * pi).sin(), -0.2 * (s * pi).sin());
    m = m * M4::translate(sx * 0.56, -0.52 - 0.6 * e, -0.72);
    let f = (s * s * pi).sin(); let g = (r * pi).sin();
    m = m * M4::ry(sx * (45.0 - 20.0 * f)) * M4::rz(sx * -20.0 * g) * M4::rx(-80.0 * g) * M4::ry(sx * -45.0);
    m * display(d, left) * M4::translate(-0.5, -0.5, -0.5)
}
fn display(d: &Disp, left: bool) -> M4 {
    let (ry, rz, tx) = if left { (-d.rot[1], -d.rot[2], -d.tr[0]) } else { (d.rot[1], d.rot[2], d.tr[0]) };
    M4::translate(tx / 16.0, d.tr[1] / 16.0, d.tr[2] / 16.0) * M4::rx(d.rot[0]) * M4::ry(ry) * M4::rz(rz) * M4::scale(d.sc)
}
```

### 11.3. Экструзия
```rust
/// alpha[y*16 + x]; результат — полоски (сторона, уровень, min, max) в порядке обхода Java; лицо/изнанка — всегда.
pub fn extrude(alpha: &[u8; 256]) -> Vec<(Side, u8, u8, u8)> {
    let opaque = |x: i32, y: i32| (0..16).contains(&x) && (0..16).contains(&y) && alpha[(y * 16 + x) as usize] != 0;
    let mut out: Vec<(Side, u8, u8, u8)> = Vec::new();
    for y in 0..16 { for x in 0..16 {
        if !opaque(x, y) { continue; }
        for (side, dx, dy) in [(Side::Up, 0, -1), (Side::Down, 0, 1), (Side::Left, -1, 0), (Side::Right, 1, 0)] {
            if opaque(x + dx, y + dy) { continue; }
            let vert = matches!(side, Side::Up | Side::Down);
            let (level, k) = if vert { (y as u8, x as u8) } else { (x as u8, y as u8) };
            match out.iter_mut().find(|f| f.0 == side && f.1 == level) {
                Some(f) => { f.2 = f.2.min(k); f.3 = f.3.max(k); }
                None => out.push((side, level, k, k)),
            }
        }
    }}
    out
}
```

`Held::tick` — последовательности §10.3; `item_pose` — матрицы §10.1 и точки §10.2; еда — `h` §10.4.
