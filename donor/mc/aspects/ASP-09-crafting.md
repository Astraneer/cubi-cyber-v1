## 0. Главное

1. **Как сопоставляется рецепт.** Сетка обрезается до рамки непустых клеток. Рамка сравнивается с обрезанным узором той
   же ширины и высоты — прямо или **зеркально по горизонтали**.
   - Сначала сравнивается число непустых клеток: лишний предмет в любой клетке ломает рецепт.
   - Переворота по вертикали нет: кирка «вверх ногами» не крафтится.
   - Положение рамки в сетке не важно. Пустые клетки **внутри** рамки важны: две доски через пропуск — не палки.
   - [src] `CraftingRecipeInput.createPositioned`, `RawShapedRecipe.matches`.
2. **Ингредиент проверяет только предмет.** Количество, износ и прочие компоненты не важны [src] `Ingredient.test`.
   Каждая клетка с тегом проверяется отдельно, поэтому доски разных пород в одном рецепте смешиваются.
3. **Слот результата показывает итог одного крафта** (4 доски при любом числе брёвен). Он пересчитывается при каждом
   изменении сетки: клик, перетаскивание, двойной клик, Shift-клик в сетку и из неё, цифры, Q, взятие результата
   [src] `CraftingInventory.setStack/removeStack` → `onContentChanged` → `CraftingScreenHandler.updateResult`.
4. **Взятие результата** тратит одну штуку из каждой непустой клетки рамки и кладёт остаток рецепта (`recipeRemainder`).
   **В нашем объёме остатков нет.** В крафте 1.21.1 остаток бывает только у торта (вёдра молока) и у мёда (бутылки)
   [data; расчёт: просмотрены все 1291 рецепт]. Остаток «ведро лавы → ведро» встречается только у топлива печи (ASP-10).
5. **Shift-клик результата** повторяет «крафт + перенос», пока в слоте результата лежит **тот же предмет**. Он
   останавливается, когда:
   - кончился самый малый стек;
   - остаток сетки сложился в другой рецепт (кольцо сундука → палки);
   - в инвентаре нет места. Излишек последнего крафта при этом выбрасывается.
   [src] `ScreenHandler.internalOnSlotClick`, `quickMove`.
6. **Верстак.** ПКМ открывает окно 3×3: рука машет, звука нет. Каждый тик проверяются два условия:
   - в этой клетке всё ещё верстак;
   - квадрат расстояния от глаз до **коробки блока** меньше `(4.5 + 4.0)² = 72.25`.

   Если одно не выполнено, окно закрывается [src] `ScreenHandler.canUse`, `PlayerEntity.canInteractWithBlockAt`,
   `ServerPlayerEntity.tick`. **Ходить с открытым окном нельзя**: клавиши получает окно. Поэтому «отойти на 9 блоков»
   не выйдет. Окно закроется при падении, толчке или если пропадёт блок.
7. **Закрытие окна верстака.** Сначала курсор, потом клетки 0…8 по порядку уходят **в инвентарь** (`offerOrDrop`). На
   землю вещь падает, только если нет места. Так же устроено закрытие 2×2 (ASP-08 §4).
8. **Причуда верстака.** Пока открыт верстак, Shift-клик по предмету в рюкзаке или хотбаре кладёт его **в сетку 3×3**:
   сначала докладывает к такому же стеку, потом в первую пустую клетку. Только если в сетку не влезло, предмет уходит
   рюкзак ↔ хотбар. В окне инвентаря (2×2) такого нет [src] `CraftingScreenHandler.quickMove`.
9. **Если подходят два рецепта**, берётся первый в списке, а порядок списка в Java произвольный (HashMap). Для объёма
   это неважно: **ни одна сетка не подходит двум рецептам**. Это проверено попарно для наших 46 рецептов и для каждого
   из них против всех 888 формованных и бесформенных рецептов 1.21.1 [расчёт].
10. **Звука у крафта нет** ни при взятии результата, ни при открытии верстака [src] `CraftingResultSlot`,
    `CraftingTableBlock.onUse`. В `SoundEvents` есть только `ui.loom/stonecutter/cartography_table.take_result`.

## 1. Порядок операций

### 1.1 Открытие верстака (фаза ПКМ тика, ASP-05 §1, §11.1)
1. Луч попал в верстак, вызывается `interact_block`. Если игрок **приседает и в руке что-то есть**, использование блока
   пропускается и предмет ставится. Shift+ПКМ пустой рукой открывает окно [src] `ClientPlayerInteractionManager.interactBlockInternal`.
2. `CraftingTableBlock.onUse`: на клиенте SUCCESS (взмах без «переподъёма» предмета). На сервере — `openHandledScreen`
   и статистика (нам не нужна). Проверки «закрыт сверху» нет, в отличие от сундука.
3. `ServerPlayerEntity.openHandledScreen`: если открыто другое окно, оно сначала закрывается (§1.7). Затем создаётся
   **новое** окно `CraftingScreenHandler` с **пустой** сеткой 3×3 и запомненными (мир, pos). Сетка живёт только в этом окне.
4. Клиент, `MinecraftClient.setScreen`:
   - курсор мыши освобождается, `KeyBinding.unpressAll()` отпускает ходьбу, приседание и прыжок;
   - пока окно открыто, нажатия до привязок не доходят [src] `Keyboard.onKey`, `bl3 = currentScreen == null`;
   - мир не на паузе.

### 1.2 Изменение сетки → пересчёт результата
Пересчёт вызывают две операции хранилища сетки [src] `CraftingInventory`:
- любая запись в клетку (`setStack`);
- любое непустое взятие (`removeStack(slot, n)`).

Обе ведут в `onContentChanged` → `updateResult`:
1. Сетка превращается в `CraftingRecipeInput` с обрезкой (§2.1). Если сетка пуста, результат пуст.
2. `RecipeManager.getFirstMatch(CRAFTING, вход, мир, null)`. Подсказки «прошлый рецепт» здесь нет: её передаёт только
   книга рецептов (`onInputSlotFillFinish`). `onContentChanged` передаёт `null`.
3. Рецепт нашёлся → `shouldCraftRecipe`. Правило `doLimitedCrafting` по умолчанию выключено, поэтому ответ всегда
   «да». Результат — копия выхода рецепта. Рецепт не нашёлся → пусто.
4. Слот результата **перезаписывается**: старое предложение просто пропадает, вещью оно не было.

Где пересчёта нет [вывод]:
- `ScreenHandler.insertItem` докладывает к лежащему такому же стеку через `slot.markDirty()`, а `CraftingInventory.markDirty`
  ничего не делает. Меняется только количество, а оно на рецепт не влияет, так что результат и так верен.
- В пустую клетку `insertItem` пишет через `setStack`, и пересчёт есть.

### 1.3 Поиск рецепта (алгоритм, эквивалентный Java)
1. **Рамка.** Крайние столбцы и ряды, где есть непустые клетки. `n` — число непустых клеток. При `n = 0` результата нет.
2. **Каждый рецепт по порядку списка.**
   - **Формованный.** Нужно одновременно:
     - `n` равно числу непустых клеток узора;
     - ширина и высота рамки равны узору;
     - узор подходит зеркально или прямо: пустой ингредиент ↔ пустая клетка, иначе `ингредиент.test(стек)`.
   - **Бесформенный.** `n` равно числу ингредиентов, и ингредиенты можно раздать стекам по одному (паросочетание).
     Рамка 1×1 и один ингредиент — короткий путь, прямая проверка.
3. **Ответ** — первый подошедший рецепт.

### 1.4 Взятие результата (`CraftingResultSlot.onTakeItem`)
Срабатывает после действий из ASP-08 §2.1–2.5:
- ЛКМ или ПКМ по результату: весь стек уходит в курсор, частично взять нельзя;
- ЛКМ или ПКМ с тем же предметом в курсоре, если результат влезает целиком;
- цифра при пустой ячейке хотбара;
- Q или Ctrl+Q: выбрасывается весь результат;
- Shift-клик (§1.5).

Шаги:
1. Статистика «скрафчено N» и разблокировка рецепта в книге — нам не нужны (`onCrafted`, `unlockLastRecipe`).
2. Обрезанный вход строится заново, **с позицией** (левый, верхний), и рецепт ищется заново. По найденному рецепту
   получается список остатков для клеток рамки: если у предмета есть `recipeRemainder`, остаток — новый стек этого
   предмета [src] `RecipeManager.getRemainingStacks`, `Recipe.getRemainder`.
3. Клетки рамки обходятся по рядам, сверху вниз и слева направо. Для каждой:
   1. непустая → `removeStack(клетка, 1)`, и это снова вызывает пересчёт (§1.2);
   2. если есть остаток:
      - клетка опустела → остаток кладётся в неё;
      - в клетке такой же предмет с теми же компонентами → остаток прибавляется;
      - иначе → в инвентарь (`insertStack`), а не влез — бросок вперёд без владельца.
4. После шага 3 результат пересчитан по новой сетке. Промежуточные пересчёты внутри шага 3 никто не видит, поэтому
   у нас достаточно одного пересчёта в конце [вывод].

### 1.5 Shift-клик результата (`QUICK_MOVE` по слоту 0)
[src] `ScreenHandler.internalOnSlotClick` + `quickMove` окна:
1. `r = quickMove(0)`:
   1. Стек результата переносится `insertItem` в инвентарь **с конца**: у игрока — слоты 9…44, у верстака — 10…45.
      - Сначала он докладывается ко всем таким же неполным стекам: хотбар справа налево, потом рюкзак снизу вверх.
      - Потом ложится в **одну** первую пустую клетку в том же порядке.
   2. Если ничего не перенеслось, вернуть пусто. Сетка не тратится.
   3. Если всё ушло, слот результата очищается.
   4. `onTakeItem` (§1.4): сетка −1, пересчёт.
   5. Что не влезло — **бросок** (`dropItem`, без владельца).
   6. Вернуть копию исходного результата.
2. Пока `r` не пуст **и** в слоте результата сейчас тот же **предмет**, снова вызвать `quickMove(0)`. Сравнение —
   `ItemStack.areItemsEqual`: без компонентов и без числа.

Следствия [вывод, проверено черновым тестом §10.1]:
- 10 брёвен → 10 повторов → 40 досок одним стеком в правой ячейке хотбара (если она пуста).
- Неделимые результаты (инструменты) ложатся по одному в пустые ячейки хотбара справа налево.
- Кончился самый малый стек → результат пуст → стоп. Остальные ингредиенты остаются в сетке.
- Остаток сетки сложился в **другой** рецепт → в слоте другой предмет → стоп. Новый результат виден, но не скрафчен.
- Частичный перенос бывает только тогда, когда пустых ячеек уже нет, а такие же стеки полны. Тогда следующий
  `insertItem` ничего не переносит, и цикл встаёт. На земле лежит излишек ровно одного крафта.
- Если бы остаток сетки сложился в другой рецепт **того же предмета**, цикл продолжился бы. В объёме таких пар нет.

### 1.6 Каждый тик: окно верстака ещё доступно?
[src] `ServerPlayerEntity.tick` → `currentScreenHandler.canUse(player)` → у верстака
`ScreenHandler.canUse(context, player, Blocks.CRAFTING_TABLE)`:
1. В клетке `pos` всё ещё верстак? Нет (сломан, заменён) → закрыть.
2. Дальность:
   - `d = 4.5 + 4.0 = 8.5`, где 4.5 — атрибут `player.block_interaction_range` (`PlayerEntity.createPlayerAttributes`);
   - по каждой оси берётся расстояние от глаз до отрезка коробки `[x, x+1]×[y, y+1]×[z, z+1]`, а если глаз внутри — 0;
   - глаза: позиция + 1.62 стоя (`PlayerEntity.DEFAULT_EYE_HEIGHT`);
   - сумма квадратов `< d²` → окно остаётся, иначе закрыть [src] `Box.squaredMagnitude`.

   С открытым окном приседание отпущено (`unpressAll`), поэтому глаза на высоте стоя [вывод].
3. Закрытие — §1.7, текущим снова становится окно игрока.

У окна инвентаря `canUse` всегда true. Клиент дальность не проверяет.

### 1.7 Закрытие (E, Esc, само, открытие другого окна, смерть)
[src] `ServerPlayerEntity.onHandledScreenClosed` → `onClosed`:
1. **Курсор.** Игрок жив → `offerOrDrop` (ASP-08 §1.2):
   - сначала такие же стеки с местом: выбранный слот, вторая рука, 0…35;
   - потом первая пустая ячейка;
   - места нет → бросок вперёд без владельца.

   Игрок мёртв → бросок.
2. **Верстак.** Клетки 0…8 (ряды сверху вниз) уходят так же, по одной (`dropInventory`). Окно и его сетка
   выбрасываются. Результат не возвращается: это не вещь.
3. **Инвентарь (2×2).** Сначала очищается результат, потом уходят клетки 0…3 (ASP-08 §4).

Если окно закрылось само (§1.6), клиент получает «закрыть экран» и снова захватывает мышь. У нас в браузере захват без
жеста пользователя может не сработать — нужна та же заглушка «клик — продолжить», что и для Esc в ASP-08 §12.

## 2. Модель: вход, ингредиент, рецепт

### 2.1 Вход и обрезка [src] `CraftingRecipeInput.createPositioned`, `RecipeInputInventory.createPositionedRecipeInput`
- Сетка хранится плоским списком: клетка `(x, y)` = индекс `x + y·w`. У 2×2 `w = 2`, у 3×3 `w = 3`.
- Рамка — от первого до последнего непустого столбца и ряда **по всей сетке**. Пустой столбец или ряд внутри рамки
  остаётся. Пример: доски в (0,0) и (2,0) дают рамку 3×1 с пустой серединой.
- Пустая сетка — пустой вход, `isEmpty`, рецептов нет.
- `stackCount` — число непустых клеток. Каждая клетка идёт в счётчик бесформенного сопоставления как 1, какое бы ни
  было количество (`matcher.addInput(stack, 1)`).
- Вход с позицией `(input, left, top)` нужен только при расходе (§1.4), чтобы попасть в клетки исходной сетки.

### 2.2 Ingredient [src] `Ingredient`
- Ингредиент — набор вариантов: предметы или теги (тег раскрывается в список предметов). В рецепте факела вместо тега
  стоит список «уголь | древесный уголь».
- `test(стек)`: пустой ингредиент подходит только к пустой клетке. Непустой подходит, если **предмет** стека в списке.
  Количество, износ, имя и чары не смотрятся.
- Равенство ингредиентов (для симметрии): тег равен тегу с тем же id, предмет — тому же предмету с тем же числом.

### 2.3 Формованный рецепт: ShapedRecipe / RawShapedRecipe [src]
Загрузка узора (`RawShapedRecipe.Data` / `fromData`):
- 1–3 ряда одной ширины 1–3. Пробел — пустая клетка, `' '` в ключе запрещён.
- Каждый символ ключа должен встретиться в узоре, а каждый символ узора — быть в ключе.
- Узор обрезается от пустых рядов и столбцов (`removePadding`). У рецептов 1.21.1 он уже обрезан.

Поля узора:
- `ingredientCount` — непустые клетки узора;
- `symmetrical` (`Util.isSymmetrical`): ширина 1 или каждый ряд читается одинаково с обеих сторон (по равенству
  ингредиентов).

**Флаг `symmetrical` — только экономия.** У симметричного узора зеркальная проверка совпадает с прямой, поэтому итог
всегда «прямо ИЛИ зеркально» [вывод]. Несимметричны в объёме: топоры, мотыги, ножницы.

`matches(вход)` — проверки по порядку:
1. Непустых клеток входа ≠ `ingredientCount` → нет.
2. Ширина или высота ≠ узора → нет. Значит, 3×3-узор в 2×2 невозможен.
3. Узор несимметричен → зеркальная проверка: клетка `(x, y)` сравнивается с узором `(w − 1 − x, y)`.
4. Прямая проверка.

Прочее:
- `craft` = копия выхода (предмет и число);
- `fits(w, h)` — только для книги рецептов, в сопоставлении не участвует;
- `group`, `category`, `show_notification` — тоже для книги, нам не нужны.

### 2.4 Бесформенный рецепт: ShapelessRecipe [src]
- Загрузка: 1–9 непустых ингредиентов.
- `matches`: непустых клеток ≠ числу ингредиентов → нет. Рамка 1×1 и один ингредиент → прямой `test`. Иначе
  `RecipeMatcher.match`: можно ли каждому ингредиенту выдать свой стек (паросочетание по битовой матрице).
- В объёме все бесформенные рецепты — с одним ингредиентом: доски, слитки из блока, самородки, сырое железо и уголь из
  блоков. Общий случай нужен будущим рецептам (огниво: слиток + кремень).

### 2.5 RecipeManager: порядок поиска и два совпадения [src] `RecipeManager.apply/getFirstMatch`, `JsonDataLoader.prepare`
- Рецепты грузятся из JSON в `HashMap<Identifier, …>` и раскладываются по типам в порядке обхода карты. Порядок
  произвольный, но стабильный. Javadoc `getFirstMatch`: «если совпадений несколько, результат произвольный».
- `getFirstMatch(тип, вход, мир, подсказка)`: пустой вход → ничего. Подсказка подходит → она. Иначе первый
  подходящий из списка типа `CRAFTING` (обычные и особые рецепты вместе).
- **Для объёма приоритет не нужен** [расчёт, скрипт по mcmeta]:
  - ни одна пара из наших 46 рецептов не может подойти к одной сетке;
  - ни один из 46 не пересекается ни с одним из 888 формованных и бесформенных рецептов 1.21.1;
  - проверялось: размер рамки, число клеток, пересечение наборов предметов поклеточно с учётом зеркала, паросочетание
    для бесформенных.

  Предложение: искать по порядку своей таблицы и держать тест «нет пересечений» (§10.1, t10).
- Особые рецепты (`crafting_special_*`) задаются кодом, а не узором. В объёме возможен только «починка» (§2.7).

### 2.6 Остатки [src] `Recipe.getRemainder`, `Item.Settings.recipeRemainder`, `Items`
- У предметов с `recipeRemainder` (ведро воды, ведро лавы, ведро молока → ведро; бутылка мёда, драконье дыхание →
  бутылка) остаток после крафта — новый стек этого предмета.
- В крафте 1.21.1 такие ингредиенты есть только в двух местах [data; расчёт]:
  - `cake` — ведро молока;
  - `honey_block` и `sugar_from_honey_bottle` — бутылка мёда.

  Вёдер воды и лавы нет ни в одном рецепте. В нашем объёме остатков нет.
- Поле остатка в реестре предметов всё равно нужно: печь возвращает пустое ведро после ведра лавы (ASP-10).
- Если при взятии рецепт не нашёлся, Java отдаёт «остатками» сами входные стеки. Это путь к удвоению, в обычной игре
  недостижимый. **Не повторяем**: расход вызывается только при найденном рецепте.

### 2.7 Особый рецепт «починка» (справочно; P2) [src] `RepairItemRecipe`
- Ровно два непустых стека в любых клетках, **один и тот же** предмет с прочностью, оба по 1 штуке. Подходит и к целым.
- Результат — новый предмет того же вида. Пусть `max` — прочность предмета:
  - `ост = (max − изн1) + (max − изн2) + ⌊max·5/100⌋`;
  - износ результата = `max(max − ост, 0)`.
- Бонус `⌊max·5/100⌋`: дерево 2, камень 6, железо 12, кожаный шлем 2. Чары пропадают, проклятия остаются (у нас чар нет).
- Работает в 2×2. Вне объёма ASP-06 (P2), решение — §12.

## 5. Граничные случаи (что чувствует игрок)

**Сопоставление**
1. **Смещение в 3×3.** Рецепт работает в любом месте сетки, где помещается:
   - палки и факел — 6 положений (3 столбца × 2 высоты);
   - верстак — 4;
   - лопата и меч — 3 столбца;
   - топор и мотыга — 2 положения × 2 зеркальные формы;
   - шлем и ботинки — верхний или нижний ряд пары рядов.

   В 2×2 палки и факел — в любом из двух столбцов.
2. **Зеркало.** Топор, мотыга и ножницы крафтятся и зеркально. Кирка, ведро и шлем симметричны, но перевёрнутые по
   вертикали не крафтятся.
3. **Лишний предмет** в любой клетке, даже такой же доски, убирает результат: не совпадает число клеток. Убрал лишнее —
   результат сразу вернулся.
4. **Пропуск внутри формы.** Две доски через пустую клетку по вертикали — не палки (рамка 1×3).
5. **Разные доски** в палках, верстаке, сундуке, инструментах — работает. Доски из брёвен — только своей породы.
   Два бревна в разных клетках — пусто.
6. **Количество не важно.** 1 и 64 бревна в клетке показывают одно и то же: «4 доски».

**Взятие результата**
7. Взятие уменьшает каждую непустую клетку на 1 и сразу показывает следующий результат.
8. ПКМ по результату берёт **весь** результат (4 доски), а не половину.
9. Курсор с 61 доской, результат 4 — клик ничего не делает (65 > 64).
10. Быстрые клики по результату с тем же предметом в курсоре крафтят по разу на клик, пока курсор не заполнится
    (второй клик двойного клика — тоже крафт).

**Shift-клик результата**
11. Кончился самый малый стек → крафт остановился, лишние ингредиенты остались.
12. Остаток сложился в другой рецепт → крафт остановился, в слоте результата виден новый предмет. Пример: кольцо
    сундука, где две верхние клетки левого столбца по 2 доски, — 1 сундук, потом в результате палки.
13. При почти полном инвентаре излишек последнего крафта падает на землю.
14. При полном инвентаре — ничего, сетка не тратится.

**Перенос в сетку и из неё**
15. **Shift-клик из рюкзака при открытом верстаке** кладёт предмет в сетку: весь стек в первую пустую клетку (слева
    сверху). Если в сетке такой же предмет, сначала докладывает к нему, остаток — в следующую пустую. Так легко
    случайно получить «две доски в ряд» (пусто). В 2×2 Shift-клик всегда хотбар ↔ рюкзак.
16. Перетаскивание по сетке (ASP-08 §2.6): результат пересчитывается после тяги. 64 доски, протянутые по 8 клеткам
    кольца, дают по 8 → сундук; Shift-клик → 8 сундуков.
17. Двойной клик собирает в курсор и из сетки (сетка идёт первой: клетки 1…9 раньше рюкзака). Результат после этого
    пересчитывается или пропадает.

**Окно верстака**
18. Закрытие: вещи из сетки возвращаются в инвентарь, не обязательно в те ячейки, откуда взяты (место ищется заново).
    Без места — падают перед игроком.
19. Повторное открытие того же верстака — пустая сетка: вещи вернулись при закрытии.
20. ПКМ по верстаку с блоком в руке открывает окно, а не ставит блок. Shift+ПКМ с блоком — ставит. Shift+ПКМ пустой
    рукой — открывает (ASP-05 §7.5).
21. В окне нельзя ходить и приседать. Окно закрывается само, только если игрока сдвинуло (падение, толчок) на

## 6. Чего нет в исходнике / не ясно

1. **Порядок рецептов в Java произвольный.** Для объёма неважно (§2.5). Если позже появятся пересекающиеся рецепты,
   нужен свой порядок или явный приоритет. Ваниль ответа не даёт.
2. **Путь «рецепт не найден при взятии»** (§2.6) в Java ведёт к удвоению, но недостижим. У нас не повторяется.
3. **Сложение остатка с клеткой** (§1.4, шаг 3.2) в Java не проверяет предел стека: например, 16 вёдер + 1. В объёме не
   встречается. Предложение — сначала ограничивать `max`, лишнее отдавать в инвентарь [не проверено в игре].
4. **Автозакрытие без внешних сил не проверить.** Сил, которые двигают игрока с открытым окном, у нас пока две —

6. **Строки** «Создание» и «Инвентарь» — по памяти [не проверено]. У нас свои строки.

```rust
    pub fn at(&self, x: usize, y: usize) -> &ItemStack { &self.cells[x + y * self.w] }
    /// рамка непустых клеток по всей сетке; None — сетка пуста
    pub fn trim(&self) -> Option<Trim> {

        for y in 0..self.h { for x in 0..self.w {
            if !self.at(x, y).is_empty() { l = l.min(x); r = r.max(x); t = t.min(y); b = b.max(y); n += 1; }
        } }
        (n > 0).then(|| Trim { left: l, top: t, w: r - l + 1, h: b - t + 1, n })
    }
}

enum Kind { Shaped(Pattern), Shapeless(Vec<Ing>) }
pub struct Recipe { pub name: &'static str, pub out: ItemId, pub count: i32, kind: Kind }

impl Recipe {
    pub fn matches(&self, g: &Grid, t: &Trim) -> bool {
        match &self.kind {
            Kind::Shaped(p) => {
                if t.n != p.n || t.w != p.w || t.h != p.h { return false; }
                (!p.symmetric && fits(p, g, t, true)) || fits(p, g, t, false)
            }
            Kind::Shapeless(ings) => t.n == ings.len() && assign_all(ings, &non_empty_in(g, t)),
        }
    }
}
fn fits(p: &Pattern, g: &Grid, t: &Trim, mirror: bool) -> bool {
    (0..p.h).all(|y| (0..p.w).all(|x| {

        let s = g.at(t.left + x, t.top + y);
        match &p.cells[px + y * p.w] { None => s.is_empty(), Some(i) => i.test(s) }
    }))
}

    pub fn find(&self, g: &Grid) -> Option<(usize, Trim)> {

    }
    /// что показывает слот результата: итог одного крафта

        self.find(g).map_or(ItemStack::EMPTY, |(i, _)| ItemStack { item: self.list[i].out, count: self.list[i].count, damage: 0 })
    }
    /// взятие результата: в рамке −1 из каждой непустой клетки, потом остаток рецепта
    pub fn consume(&self, g: &mut Grid, remainder: &dyn Fn(ItemId) -> Option<ItemId>, give: &mut dyn FnMut(ItemStack)) {
        let Some((_, t)) = self.find(g) else { return };            // без рецепта — ничего (в Java тут дюп)
        // остатки считаются ДО расхода, по клеткам рамки
        let rems: Vec<Option<ItemId>> = (0..t.w * t.h).map(|k| {
            let s = g.at(t.left + k % t.w, t.top + k / t.w);
            if s.is_empty() { None } else { remainder(s.item) }
        }).collect();
        for k in 0..t.w * t.h {
            let i = (t.left + k % t.w) + (t.top + k / t.w) * g.w;
            let mut s = g.cells[i];
            if !s.is_empty() { s.count -= 1; if s.count <= 0 { s = ItemStack::EMPTY; } }
            if let Some(r) = rems[k] {
                let r = ItemStack { item: r, count: 1, damage: 0 };
                if s.is_empty() { s = r; }
                else if s.item == r.item && s.damage == r.damage { s.count += 1; }  // предел — §6.3
                else { give(r); }                                                  // в инвентарь, иначе бросок
            }
            g.cells[i] = s;
        }
    }
```

```rust
        if self.slots[id].store == Store::Craft { *st.result = cx.book.result(st.craft); }   // onContentChanged
    }
    fn on_take(&self, st: &mut Stores, id: usize, cx: &mut Ctx) {
        if self.slots[id].kind == Kind::Result {
            let (player, ev, reg) = (&mut *st.player, &mut *cx.ev, cx.reg);
            cx.book.consume(st.craft, &|i| reg.remainder(i), &mut |mut s| {
                if !player.insert(&mut s, reg) || !s.is_empty() { ev.push(InvEvent::Drop { stack: s, throw: Throw::Forward, owned: false }); }
            });
            *st.result = cx.book.result(st.craft);
        }
    }
    fn quick_move_crafting(&mut self, st: &mut Stores, id: usize, cx: &mut Ctx) -> ItemStack {
        // 0      → insert_item(10, 46, rev = true); если что-то ушло: on_take; остаток — Drop
        // 10..46 → insert_item(1, 10, false), иначе (id < 37 ? insert_item(37, 46) : insert_item(10, 37))
        // 1..10  → insert_item(10, 46, false)
        unimplemented!()
    }
    /// раз в тик, после движения игрока
    pub fn tick_validity(&mut self, st: &mut Stores, world: &World, eye: [f64; 3], cx: &mut Ctx) {
        if let MenuKind::Crafting { pos } = self.kind {
            let ok = crafting_table_in_reach(eye, pos.into(), world.block(pos) == CRAFTING_TABLE);
            if !ok { self.close(st, cx); cx.ev.push(InvEvent::ScreenClosed); }
        }
    }
    // close(): курсор → offer_or_drop; Crafting — клетки 0..9 → offer_or_drop; Player — результат = EMPTY, клетки 0..4
}
```

`Shift`-цикл ASP-08 `while !r.is_empty() && self.get(st, id).id() == r.id()` подходит без изменений: условие уже
сравнивает только предмет.

## 12. Что решить главному агенту / пользователю

1. **Список рецептов.** Подтвердить 46 записей §4.2. Сейчас бесполезны: самородки (ни на что не идут), кожаная броня
   (нет коров), блоки железа, сырого железа и угля. Предложение — держать: рецепты дешёвые, иконки и блоки нужны всё
   равно (блоки — опц. в ASP-06).
2. **Починка двумя предметами** (§2.7) — дёшево, работает в 2×2, игроки её знают. Брать сразу с износом или отложить.
3. **Shift-клик из инвентаря в сетку верстака** (§0.8) — ванильная причуда, сбивает новичков. По решению «причуды
   повторяем» — повторять. Подтвердить.
4. **Ванильные рецепты из тех же материалов** (§4.4) — пусто, как сейчас, или добавить дешёвые без новых блоков: миска
   и огниво бесполезны без еды и огня. Предложение — ничего не добавлять. Плиты, ступени, двери и заборы требуют новых
   форм блоков (E5/E8) — отдельный объём.
5. **Способ проверить автозакрытие** (§7, шаг 16): отладочная клавиша «сдвиг игрока на +10 по X» или только падение.
   Предложение — отладочная клавиша рядом с «выдать предметы».
6. **Предел стека при сложении остатка** (§6.3): ограничивать `max` (предложение) или как в Java. В объёме не
   встречается.
7. **Где хранится сетка.** 2×2 — у игрока (всегда пуста при закрытом окне), 3×3 — в окне верстака. Предмет не
   сохраняется между открытиями — как в ваниле.
