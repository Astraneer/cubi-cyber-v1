# Полный серверный прогон §8.6

Тяжёлая проверка запускается явно из корневого графа зависимостей:

```sh
source tools/env.sh
CARGO_INCREMENTAL=0 cargo test --release --locked --offline -p server --test spec86_owner -- --ignored --nocapture
```

Обычный `cargo test` её пропускает. Это проверка настоящего `Runtime` и сохранения,
не вызов отдельного вычислительного ядра. 32 клиента используют настоящие UDP
сокеты и штатный аутентифицированный Channel. Клиенты работают в отдельном потоке;
профиль в каждом направлении — 75±20 мс, 2% потерь с переупорядочением. Лимиты
буферов и повторов не увеличиваются. Перед нагрузкой клиенты действительно входят,
получают серверную телепортацию и обмениваются ping; все 32 запроса публичных страниц
должны завершиться к концу нагрузки.

В исходном сохранении находятся 5000 настоящих Pig, 10000 Smelter-компонентов с
энергией и входными предметами и 100000 известных клеток WATER. События воды имеют
общий ближайший срок, затем должны фактически обработаться все; будущая холодная
очередь не считается выполненной работой. Снимок и подготовка отделены от замера.
В замер входят полные `Runtime::poll`, захват владельцем, кодирование, копии передачи
писателю и применение подтверждённых данных. Ручные checkpoint захватываются
отдельно тем же счётчиком аллокаций. JSONL содержит логические тики, работу, байты,
возраст исходной просрочки, фактический WAL и численные показатели каждого клиента.
Время записывается справочно, аппаратного порога миллисекунд в проверке нет.

Выборка машин сравнена с медленным `rules::Machine.tick` по одному вызову на каждый
прошедший глобальный тик; у всех 10000 дополнительно проверены энергия, прогресс
и сохранение количества входа/выхода. После 400 рабочих тиков исходная энергия
заканчивается: дальнейший сон соответствует эталону. Это не утверждение, что
10000 рецептов продолжали работать без энергии весь срок обработки воды.

Теперь граница Prepare → Machines → Resources → Transit долговечна. Каждая порция
удерживает один глобальный тик, конечный состав событий и порядок создания;
ресурсы выполняются до транспорта. Подготовленные строки учитываются отдельно
от исполненных событий. Отдельные проверки покрывают 10000 активных Smelter по
одному шагу в каждом из трёх тиков, 42 тика настоящей сети с PULL/пакетами при
одно-событийных порциях и открытие настоящего Store после каждой порции.
Неизвестный вход переносится на следующий тик. Маршрут, превышающий фиксированный
предел поиска, выдаёт явную ошибку, не оставляет незавершаемый скрытый цикл.

Контекст частичного тика сохраняет активные страницы и идентификаторы участников.
Kind2-конверт MOP1 сохраняет фактический остаток группы существ, включая посещённые
Unknown-тела без изменения строки. Три настоящие проверки до повторного Hello
сравнивают непрерывный сервер с открытым журналом: 2049 Cube с сохранением всей
энергии и подбором предметов; 1025 существ с ударом зомби по восстановленному игроку;
та же группа с уже посещённым Unknown. Проверяются World hash, все runtime-байты,
инвентарь, здоровье, окно и продолжение физики игрока. Отрицательная
проверка 2049 светящихся Smelter сохранена; после добавления частного kind8 она
также проходит и сравнивает точное продолжение промежуточной очереди LIGHT при
восстановлении (`lighting::continuation_tests`).

Сетевой приём больше не вызывает симуляцию для каждого сообщения: Runtime
принимает ограниченную порцию входящих данных, затем вызывает владельца один раз.
Прямой `Server.handle` сохраняет немедленное поведение. Фактический прогон проверяет
каждый `Runtime::poll`: максимум 2048 подготовленных строк, 2048 шагов машин и
1024 шага существ. Проверка настоящего UDP burst с быстрым писателем дополнительно
показывает, что 32 входящих сообщения не запускают дополнительные фазы. На этом
запуске максимальное выделение за poll — 78146653 байта, время — 274856 мкс;
оба показателя справочные, требование 25 мс ими не принимается.

Расходы владельца измерены целиком: 130848025625 суммарно выделенных байт,
3785360875 байта передачи runtime писателю и столько же входных байт повторного
применения, 148015078 байт runtime при захватах checkpoint. Это накопленные
выделения, не одновременно занятая память. Во время 32 холодных тиков суммарно
выделено 184943690 байт: в сценарии остаются 32 сетевых игрока-наблюдателя, их
состояния и транспорт. Нулевые runtime-байты не означают нулевую стоимость всего
сервера. Аппаратные требования к миллисекундам этим прогоном не принимаются.

Плотная группа вызвала 13162 явных переполнений публичного AOI сущностей; предел
2048 поз сохранялся, пропущенный кадр не считался доставкой. Все 32 клиента всё же
получали кадры. Это не проверка одновременной видимости всех 5000 у каждого клиента.

Предыдущий прогон V2 оборвался по сроку надёжного UDP-кадра. Отдельная направленная
проверка нашла и исправила блокировку транспортных ACK полной канонической
входной очередью: ACK продолжают обрабатываться в том же бюджете чтения, новые
данные не подтверждаются до освобождения места. Аутентификация, размеры очередей
и сроки повторов сохранены. В успешных полных прогонах счётчик входного давления равен нулю,
поэтому их успех сам по себе не доказывает причину того сбоя V2.

Обычный debug workspace-тест сохраняет явный `ignore` для тяжёлого сценария.
Отдельный обязательный CI job `server_scale` запускает его в release через
`bash tools/check_server_scale.sh`, сохраняет исходный SHA, JSONL и журнал при любом
результате и имеет конечный timeout 35 минут. Дополнительная проверка требует
свежий маркер именно выполненного теста и полный отчёт; ноль запущенных тестов
или старый JSONL не могут дать успех. Общий отчёт разрешает success и
создание PR только после успеха Linux, Windows и server_scale; отсутствие,
пропуск, отмена или ошибка нагрузки не превращаются в успех. Настройка job не
означает, что удалённый CI уже прошёл на текущем коммите.

После полного прогона отдельно измерен холодный публичный Entity-путь. Проверка
`entity_owner_idle` использует настоящий вход владельца, принятую команду spectator,
настоящий checkpoint и 1000 неподвижных существ. За ровно 1000 тиков тела не
выполняют AI, runtime не передаётся писателю и подтверждённый публичный кадр не
меняется. Пять плановых checkpoint остаются в измерении целого владельца.

До кэша неизменного источника выполнено 1000000 построений поз и 9261000 проб
пространственных корзин, выделено 198991800 байт за 177370 вызовов. После кэша —
1000 поз и 9261 проба для единственного прогревочного ACK, 43531416 байт за 21526
вызовов: на 78,1% меньше выделенных байт. Это отдельный контролируемый сценарий,
не подмена чисел предыдущего полного прогона. Журналы:
`.local/artifacts/entity-owner-idle-before.log` и
`.local/artifacts/entity-owner-idle-after.log`.

Кэш учитывает точный интерес наблюдателя, бюджет и поколения подтверждённых
Mob/Item-ledger. Запрос полного кадра, подтверждение другой базы, прямое построение
из store, замена источника и изменение интереса сбрасывают прежний результат.
Поколения существуют только в памяти, не входят в снимки, хеши и пакеты. Отдельные
проверки сохраняют восстановление полного кадра, изменения предметов и источника
с прежними длиной/ревизией. Неизменное переполнение AOI удерживает прежний кадр
без повторного полного обхода; это не превращает неполное изображение в полное.
