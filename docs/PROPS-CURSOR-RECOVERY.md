# Восстановление производного кэша моделей после пропуска журнала

Сохранённый Native Factory R7 завершился ошибкой `CPU authority continuation failed: Cursor(Lagged { expected:1110, oldest_available:1115 })`. Props показывал `caught_up:false` и возраст1359 тиков при retention1200. Это сильный признак, но прежняя строка не отличает Lighting и Props. Отдельный патч добавляет имена стадий к ошибкам; конкретный владелец исторического падения не объявляется доказанным.

PropsSource действительно передаёт Lagged из read_cursor/acknowledge_cursor без восстановления. Кандидат восстанавливает только этот производный кэш. В начале ingest проверяется собственная последовательность относительно journal_oldest. Он сохраняет текущие имена загруженных публичных страниц, удаляет частичный устаревший record и готовые результаты старых workers, затем переносит только свой cursor к границе снимка. Курсоры событий и других потребителей остаются прежними.

Копируется не более max_pages заголовков World, заново помечается не более2×max_pages уже индексированных заголовков и не более2×max_pages публичных frame-заголовков. Это отдельный ограниченный расход recovery_headers, выполняемый только при потере истории; клеток страниц здесь не читают. Повторно используемый Vec<PageId> резервируется при attach: max_pages×size_of(PageId), по умолчанию16КиБ; лимиты не повышаются.

После предварительной проверки revision старые публичные frames и hint-count сбрасываются: иначе пропущенный removal может оставить frame вне текущего списка bindings. Remote.pump_props заново публикует только кадры, связанные с актуальным публичным Raw, из существующего connection-cache с прежним бюджетом4 за pump.

Существующие слоты моделей сверяются с текущим World по одному на обычный entry-credit. Старый модельный lifetime отзывается даже при равных текущих клетках; optional temporal registration создаётся заново. Несуществующий/скрытый объект остаётся в очереди реальной hidden-публикации GPU. Старые ports/wind сбрасываются, действующий публичный frame может установить только подходящий hint. Исчезнувшие модели обрабатываются по индексу, новые находятся обычными worker-снимками4096 клеток. GPU upload, память, mesh/journal capacity и сроки не меняются.

При заполнении хранилища новый запрос страницы сохраняется и даёт backpressure: обычная hidden-публикация освобождает старые слоты/заголовки. Статус caught_up/settled остаётся false до завершения сверки, постановки текущих страниц и потребления последующих записей. Повторная потеря истории запускает новую текущую сверку; старое состояние не выдаётся за готовое.

Подготовлено11 CPU-регрессий: истёкший частичный record/один credit, удалённая и вновь появившаяся модель, старый worker с неизменным source, сброс temporal registration при равных клетках, независимые курсоры/живые игровые события нулевой бюджет, пропущенный отзыв публичного frame и атомарный отказ при переполнении его revision, а также удержание max_running резервов при повторных восстановлениях без завершения старых worker-задач и освобождение пустого заголовка страницы после старого completion/fail. Rustfmt разобрал код. Cargo, GPU и реальный новый Factory ещё не запускались; это кандидат.

Резервы running не очищаются: платформенный ViewProps ещё удерживает соответствующие contexts/retry/pending и реальные transport-задачи. Монотонный recovery_job_floor=next_job делает все ранее запущенные результаты устаревшими даже при равном source; их резерв и page.running (сохранённый без повторного поиска по всем задачам) снимаются только обычным terminal completion/fail. Поэтому повторный recovery не может допустить новую партию сверх прежнего max_running. Никакое подтверждение отмены worker или освобождение его байтов не выдумывается.

Предпосылка текущего product-клиента: общий загруженный World не превышает PropsLimits.max_pages (Scene≤512, стандартный Props≤1024). При нарушении этой границы generic API возвращает Capacity; кандидат не обещает поддержку бесконечного внешнего World через маленький VisibleRegion. Это ограничение должно оставаться явным при дальнейшем использовании API.

Отдельная проверка насыщения использует max_pages1/max_running2 и настоящие удерживаемые PropsTask A/B. После удаления B и создания C оба старых заголовка занимают2P: восстановление удерживает точный индекс C с backpressure, не увеличивает квоты и не допускает свежую задачу. Terminal fail A освобождает заголовок; C ставится в worker, terminal result B освобождает второй старый заголовок. Только текущая C может дать модель. Проверка подготовлена, но ещё не исполнена Cargo.
